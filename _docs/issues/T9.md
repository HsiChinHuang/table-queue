## Reason (audit provenance)

SEC AUDIT HIGH (A-2 A-9, D-5): login authenticates against plaintext env PIN whenever DB hash absent and default bootstrap ALWAYS leaves it absent; 12h tokens carry no jti and survive PIN rotation. Severity HIGH.

## Goal

A fresh boot of the shipped application stores the staff credential only as a bcrypt hash, verifies a submitted PIN against that hash and nothing else, and makes a PIN rotation a revocation event so that every JWT issued before the rotation is refused.

## Context

Related: Platform #64. Audit sources: `audit-A-out/report.md` A-2 (plaintext env fallback plus
`staff_pin_hash = null` bootstrap) and A-9 (12-hour tokens with no `jti`, unaffected by rotation);
`audit-D-out/report.md` D-5 (documented PIN, plaintext fallback, no lockout - the lockout and
documented-default-PIN halves of D-5 are not this issue, see Out of scope).

The whole defect is three code sites and all three are measured in "Groom baseline" below:

- `backend/app/main.py:265` - the `bootstrap_defaults` settings INSERT writes
  `staff_pin_hash ... null`, so the hash-less state is the shipped default rather than an edge case.
- `backend/app/routers/auth.py:96-101` - `_pin_matches` falls through to
  `pin == get_settings().staff_pin`, a short-circuiting `str ==` against a plaintext env value.
- `backend/app/routers/auth.py:114-121` with `backend/app/dependencies.py:70-80` - login mints
  `{sub, role, iat, exp}` and the verifier checks signature, `exp` and the presence of `sub`, so
  `change-pin` cannot invalidate anything it already issued.

Plan anchors that this issue deliberately overrides: `_docs/plan.md:596` and `:3101` state "Login
validates PIN against `Settings.staff_pin_hash`, fallback to `STAFF_PIN`", and B-05 shipped that as
ruling R-B05-3 (`backend/app/routers/auth.py:9-11`). The audit found the fallback to be the hole, so
this issue is a contract change and not a bug fix: the fallback is deleted, the plan line is stale,
and the SW round must not treat R-B05-3 as binding. `has_pin = bool(row.staff_pin_hash)`
(`backend/app/services/settings.py:207`) and `_docs/openapi.yaml:1961` stay as they are: the field is
a hash-presence flag, not a secret, and AC-8 pins that it still leaks nothing.

- Design: not a UI issue, so no `_docs/design-system.md` anchor.
- Plan: `_docs/plan.md` (B-05 auth sections, lines 590-600 and 3100-3110).

## Decision (PM, T9 groom round 1)

Four design questions had to be settled before any AC could be falsifiable. They are settled here, and
the ACs pin the chosen *behaviour*, never the chosen implementation.

**D-1 - Bootstrap derives the hash from `STAFF_PIN`; the env value stays a seed source only.**
`bootstrap_defaults` reads `settings.staff_pin` and writes `hash_pin(...)` into the row it inserts.
The env var remains the operator's one-time seed for first boot (the README/`.env.example` contract
that an operator sets `STAFF_PIN` before the first start keeps working, unrotated, exactly once);
afterwards the DB hash is the only credential. What is not optional: the env value may never be an
accepted credential (AC-2, AC-3), and a fresh boot never writes a hash-less row (AC-1). A blank or
unset `STAFF_PIN` at bootstrap is a config error, not a licence to write NULL - the AC pins either a
refused boot or a boot that fails closed (login answers 401 for every PIN, AC-5). Chosen over
generating a random PIN at first boot, which would break every documented quickstart and the demo
flow for no security gain, since the operator has to rotate either way.

**D-2 - Revocation design: a token generation secret folded into the signature, not a revocation
table.** `change-pin` rotates a server-side generation value; login signs with it and the verifier
recomputes it, so a pre-rotation JWT fails signature verification and answers 401
`AUTH_TOKEN_EXPIRED` from the existing dependency. Chosen over a revocation instant because that
cannot be checked by the existing verifier without a database read on every staff and admin request,
and chosen over a `jti` allow-list because there is no per-person identity to attach a `jti` to
(`sub` is the constant `"staff"`, so an allow-list would hold exactly one row and would be a
token-version counter wearing another name). The trade-off the SW round must not quietly widen: the
generation value has to be visible to both login and the verifier, which makes it either a settings
column or a process global, and a process global does not survive `--workers 2`
(`_docs/deployment.md:161` prescribes two workers, so tokens minted by worker A would die on worker
B). AC-5 therefore measures the storage-independent property - rotation revokes, and a login made
after the rotation still works - so whichever storage the SW picks, the multi-worker shape has to
satisfy it. `exp` / `sub` / signature semantics are unchanged and AC-8 pins them.

**D-3 - Constant-time means bcrypt-only.** The requirement is met by deleting the plaintext
comparison so the only verification path left is `bcrypt.checkpw` (A-2's own fix direction says to
replace `==` with `hmac.compare_digest` "even for the transitional path" - the transitional path is
what this issue deletes). AC-4 is a static assertion over the two auth-path files. Behavioral timing
measurement is explicitly out of scope: it would be a flaky gate, and timing side channels are not
the exposure the audit describes.

**D-4 - `has_pin` and the response shape do not move.** `read_settings` keeps reporting
`bool(row.staff_pin_hash)`. After the fix a bootstrapped store reports `has_pin: true` instead of
`false`, which is the honest answer. AC-8 pins the two properties that actually matter: the hash
never leaves the API, and the PATCH whitelist still refuses `staff_pin_hash` / `staff_pin`.

## Acceptance criteria

Eight blocks, all runnable from the repo root of the tree under test. Do not run them under `set -e`
or `set -o pipefail`, and never pipe one into a truncating consumer such as `head`: a state-changing
block that is SIGPIPEd yields a false FAIL, and rc is not the verdict here in either direction (see
each block's `Expected at groom base`). This is a FIX issue, so **every block below is expected RED at
the groom base** - they encode the fixed behaviour, and the audit evidence plus the Groom baseline
above is what shows each one red today. Each block states its own red command.

Three conventions that are load-bearing and were measured rather than assumed:

- **The tree under test must be importable.** `backend/.venv` is a symlink to the suite venv, and that
  venv ships a `pyvenv.cfg` with `home = <repo>/.venv/bin`; CPython then turns
  `backend/.venv/bin/python` into `<repo>/.venv/bin/python` via `site.getusersitepackages()`, and
  `sys.path[0]` becomes `<repo>/backend` - the main checkout, not the worktree. Every block therefore
  exports `PYTHONPATH=$PWD/backend` (measured: `IMPORT_FROM` is `/home/te/tq/suite/backend/app/main.py`
  without it, the worktree with it) and asserts `app.main.__file__` sits under `$PWD`, printing
  `BROKEN AC-n` if it does not. A block that measured the wrong tree is not a measurement.
- **Script scratch.** Blocks write their Python probes under `$TMPDIR` (which the gate env points at
  `/home/te/tq/pytest_tmp`, an ext4 path) and their SQLite file at `$PWD/_t9ac.db`, and every block
  removes both at the end. Nothing under the repo tree is created except that one `_gate`-style db
  file, and AC-9 asserts the tree is clean afterwards.
- **The database must be the one the block named.** `app.config.Settings.database_url` carries no
  default, so it cannot silently relocate; each block asserts
  `get_settings().database_url` contains its own file name before it touches a row.
- [ ] **AC-1** `bootstrap_defaults` writes a real bcrypt credential: on a fresh schema the shipped
  startup path inserts exactly one settings row whose `staff_pin_hash` is a 60-char `$2b$12$` hash
  that answers to the `STAFF_PIN` **seed** (D-1: env is the seed source, never a credential) and to
  nothing else, and that row is usable - a staff token minted from it reads
  `GET /api/v1/admin/settings` at 200. The other half of the AC is the fail-closed rule that makes
  the hash the only credential that matters: a settings row with `staff_pin_hash = NULL` - the shape
  the shipped bootstrap writes today, so a pre-fix database, a hand-deleted hash
  (`_docs/deployment.md:234` tells an operator to do exactly that), or a reset that did not seed -
  must answer **401**, not the 200 an unauthenticated caller gets today. An empty store answers 500
  from the existing `INTERNAL_ERROR` contract and that is accepted; a NULL hash answering 200 is not.
