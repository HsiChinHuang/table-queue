## Goal

Serve `GET /api/v1/admin/settings` and `PATCH /api/v1/admin/settings` behind the staff JWT, so the
admin settings screen can read and edit the single settings row - store info, waitlist knobs and the
three notification templates - and so no response on either operation can ever carry
`staff_pin_hash`.

## Context

The admin surface is the last unauthenticated gap on `main`: `app/main.py` mounts exactly two
routers, `auth.router` and `public.router`, and there is no `app/routers/admin.py` at all
(measured, see "Baseline" below). B-11 (tables) and B-12 (reset) will add more operations to the
same `admin.py` file, which is why AC-1 pins path *presence* rather than file exclusivity.

Three contract readings settle before implementation starts. Each one states the source that wins
(`_docs/specs.md` > `_docs/ui.md` > `_docs/openapi.yaml` > `_docs/testing.md`, and the contract wins
over this issue's owner stub - the B-06 AC-15 precedent).

**R-B10-1 - `SETTINGS_NOT_FOUND` is unreachable by design, and this is the issue that resolves the
`_docs/specs.md` line 479 / 484 note.** `_docs/specs.md:479` records that
`SETTINGS_NOT_FOUND` (404) "is named in the error list of Platform Issue #36 ... but
`GET/PATCH /api/v1/admin/settings` declare no 404 response and `components.responses` has no such
entry", and `specs.md:484` defers the missing `components.responses` entry to "Platform Issue #36" -
this issue. Resolution, measured rather than asserted:

- The schema makes the row unique per branch: `models.py` `Settings.branch_id` is
  `ForeignKey("branches.id"), nullable=False, unique=True`, and `_docs/specs.md:572` says
  "DB unique index on branch_id for settings". There is therefore exactly one settings row per
  branch and no id-addressable settings resource that could be missing.
- `app/main.py:bootstrap_defaults` inserts that row on every startup when the `settings` table is
  empty (B-15, Platform #47, merged, fixed the NOT-NULL crash in that INSERT), and the lifespan
  handler calls it after `Base.metadata.create_all`. So a booted app cannot reach the handler with
  no row.
- `_docs/openapi.yaml` declares `200` and `401` for GET and `200` / `401` / `422` for PATCH. There
  is no 404 and no `components.responses.SettingsNotFound`. Emitting one would be an out-of-contract
  error code, which `_docs/specs.md` section 11 forbids ("a code that no operation returns must not
  appear in this table", and the same section lists `SETTINGS_NOT_FOUND` under "Codes outside the
 API contract").
- Measured reachable-404 probe: on this `main` an unauthenticated `GET`/`PATCH` to
  `/api/v1/admin/settings` answers 401 (mounted-unknown-path behaviour was measured with
  `TestClient` at 404 `{"detail":"Not Found"}` for a path that is not registered, and with a
  registered route answers 401 without a token) - no 404 stays observable.
  Therefore: **no 404 and no `SETTINGS_NOT_FOUND` is implemented here.** AC-8 asserts 200 on the
  bootstrapped database and the absence of any 404/`SETTINGS_NOT_FOUND` path, and AC-9 asserts the
  full set of status codes the operation declares. AC-8's bash block also *measures* the
  degenerate no-row case (a row-less settings table on a server that returns 500 rather than
  inventing a 404), which is the honest cost of choosing the contract over the stub: the observable
  in that state is `500 INTERNAL_ERROR` (a code `specs.md` section 11 does specify), and if a future
  issue wants a real 404 it must first add the operation's 404 to `_docs/openapi.yaml` and a
  `components.responses` entry - that is a contract change owned by Platform Issue #3 (per
  `specs.md:484`), not a code change owned by this one.
- **Recorded divergence (visible, not silent):** the owner stub's bullet
  "Errors: `VALIDATION_ERROR`, `SETTINGS_NOT_FOUND`" is narrowed to `VALIDATION_ERROR` only. The
  other half of that bullet is unsatisfiable inside the contract as shipped.

**R-B10-2 - range and pattern validation is the shipped schema's, not a re-invention.**
`app/schemas.py` (B-03, merged) already carries `UpdateSettingsRequest` with
`hold_minutes: int | None = Field(default=None, ge=5, le=15)`,
`avg_seat_minutes: int | None = Field(default=None, ge=5, le=60)`,
`queue_prefix: str | None = Field(default=None, pattern=r"^[A-Z]{1,3}$")`, and
`open_time` / `close_time` with `pattern=r"^\d{2}:\d{2}$"`. Those bounds are identical to the
`SettingsResponse` / `UpdateSettingsRequest` bounds in `_docs/openapi.yaml` (minimum/maximum 5/15,
5/60, the same `pattern` strings), so AC-4 and AC-5 pin the shipped validators at their four
boundaries each and forbid the route layer from re-declaring a request model. `HH:MM` means what the
pattern says plus what a clock means: `24:00` passes the shipped regex and is not a time, so AC-5
grades the two time fields on the shape the contract literally enforces (regex) and separately
rejects the day-invalid `24:00` claim only inside the regex-visible set - the AC's prose says exactly
which of the two it measures rather than implying it measures a clock validator the schema does not
have.

**R-B10-3 - `notification_templates` is one JSON object that must carry all three keys.**
`_docs/specs.md` section 6 names the three keys (`joined`, `called`, `no_show`), and
`_docs/openapi.yaml` `UpdateSettingsRequest.notification_templates` declares an object whose
`properties` are exactly those three with no `required` list - so "all three keys present" is
`_docs/testing.md`'s `test_update_settings_notification_templates` plus this issue's own reading of
the shape, and it is enforced at the route layer because the shipped schema types the field
`dict[str, Any] | None` and cannot see inside it (measured: `{"joined": "x"}` validates clean against
`UpdateSettingsRequest`). AC-6 therefore measures the 422 on a partial object and the 200 on a full
one, and names the level (route layer) that owes the check. `SettingsResponse` types the same field
`dict[str, Any] | None` while the model stores a JSON *string*, so the service decodes it - AC-3
requires the dict, not the raw string.

`updated_at` is `onupdate=lambda: datetime.now(UTC)` on the model, so AC-7 pins the bump with a
frozen clock rather than a sleep, per `_docs/testing.md` "Time Injection".

## Groom defects found while measuring (round 1: four ACs could not be graded from this file as written)

AC-7, AC-8, AC-10 and AC-11 were red on the round-1 branch for a reason inside the block rather than a
reason inside the product. Round 2A repaired all four, and each repair carries the
mutation that proves it two-sided on its own `Measured today` line. Items 1 to 4 below are kept as the
history of what was measured - including three limiter doors built, measured and rejected - so the next
reader starts from the fourth door rather than the first. Items 5 to 7 are new: a product finding, a
ruling, and the deliberately unresolved red (whose mechanical half AC-15 now prices).

Two harness defects underlay items 1, 3 and the AC-10 crash and are fixed once for all fourteen blocks.
`boot()` now wipes `settings`, `branches` and `restaurants` before seeding: a second call used to die on
`UNIQUE constraint failed: restaurants.id`, which each block's `2>/dev/null` turned into the bare
`probe process exited rc=1` the gate graded red. And the throwaway settings pair is declared at
`PROBE_PATH` with `include_in_schema=False`, never at the contract path, because FastAPI answers the
FIRST full match while slowapi's resolver takes the LAST - the mismatch that made AC-10, AC-11 and
AC-13 red with no product defect behind any of them.

1. **AC-10 and AC-11: the block's own seed is invisible to the application, at the engine that ships.**
   `boot()` calls `Base.metadata.create_all(engine)` and inserts its restaurant row, and the request that
   follows answers `no such table: settings` or `UNIQUE constraint failed: restaurants.id` - a second
   `boot()` cannot see the row the first one wrote, either. `app.database.engine` is built with SQLite's
   default pool for a file-backed database, which is one connection held for the life of the process; the
   block's sessions open a *different* connection to the same URL, and that is where its tables and rows
   live. An earlier revision of this branch moved the application onto a per-request connection
   (`poolclass=NullPool`) to make the two connections agree, and the measurement came out the same:
   AC-10's `IntegrityError` and AC-11's 500 survived the change, because the second failure behind them is
   item 3. Reverting it is therefore not a cost of this branch - it changes neither AC - and it is not a
   fix either. A fix that would work is a `DATABASE_URL` the harness and the application both read through
   one engine, which is what `backend/tests/conftest.py` and every self-building test module in this suite
   already do; the blocks reach the shared engine directly instead, and rewriting that belongs to the
   harness's owner, not to the settings router.
2. **AC-7: the seed check compares a timezone-aware constant against a naive read-back, so it cannot
   hold on any tree.** `ok(stamped() == OLD, ...)` and `ok(row.created_at == OLD, ...)` compare
   `datetime(2026, 1, 1, tzinfo=UTC)` with what a `DateTime(timezone=True)` column returns from SQLite,
   and SQLite has no offset-aware `DATETIME` - the value comes back naive and both comparisons are False.
   The AC's own words are "a row seeded at 2026-01-01 answers a PATCH" and "`created_at` does not move",
   and the seed *is* 2026-01-01; the comparison is what is wrong. Fixing it is not mechanical, though:
   `OLD` is the same constant the next arm uses to mean "is still the baseline", so normalising the
   read-back would also make a `created_at`/`updated_at` that genuinely moved read as unmoved. That is an
   assertion change, not a repair, so the block stands. On the base `3db99aa` this block fails four arms,
   two of them seed checks that run before any request is issued, and `hold_minutes=10` after them - which
   is the measurement that says no handler was reached.
3. **AC-8 and AC-11: a hand-appended `APIRoute` reaches the rate-limit middleware by a path that renders
   a 500 whatever the product does.** Both blocks build `PROBE_ADMIN`, call `M.mount(...)`, and then also
   append the same `APIRoute` objects to `M.app.router.routes` because `include_router` on this FastAPI
   build registers a container rather than copying operations. AC-8's surviving 200-arm and AC-11's
   shape-arms then interrogate *that* route. Measured with the limiter disabled, the limiter enabled, the
   route mounted only, appended only, and both, in four orders, at four different revisions of this
   repository including the pre-issue base: the answer is 500 in every one. It is not the product's 500 -
   the shipped unhandled-exception handler answers `Internal server error`, and the throwaway answers
   `INTERNAL ERROR`, which is `AppError`'s code-derived default and therefore a 500 raised inside the
   middleware rather than in a handler. So the arms assert a state of a probe route, and the state is a
   property of the probe's shape. AC-8's four probe-request arms were removed on the orchestrator's
   approval because the AC-2 block asserts the same state on the real surface; AC-11's cannot be removed,
   because the shape it asserts is the subject of the AC, and its real-handler half (parameter signature,
   `response_model`) is satisfied and asserted in `backend/tests/test_admin_settings.py`.
4. **AC-13: the AC asks the product to open a door that is not there at this lock.** `GUEST_LIMIT` is a
   `default_limits` value, and a default reaches every route carrying no limit of its own, so the settings
   pair is priced and the eleventh refresh is a 429 - which is the AC's own red. Three doors were built
   and measured, and each costs more than it buys:
   * a `Limiter.exempt(handler)` entry files a handler name in a limiter constructed with
     `key_style="url"`, which prices by path; measured red at the eleventh refresh, unchanged.
   * a per-route entry in the limiter's own registry does take the surface out of the default at the
     per-route call, but the middleware assembles the limits it applies without consulting that registry,
     and on the call it does make, the request then reaches a response-header path that reads a request
     attribute no one set. Measured: the eleventh refresh answers 500 instead of escaping the budget.
   * a request filter does decline the default, and is the only one of the three that works at all - and
     it has the same 500 on the way out, because the flag that declines a request is process-wide rather
     than per path, and the two doors that would keep the middleware from pricing a response it never
     measured (`headers_enabled`, or narrowing the default to the guest paths) each take a budget away
     from B-05's login or B-06's four guest counters, whose green tests are this repository's own.
   All three revisions are in this branch's history (`a1ab627`, `f8118b5`, `0071368`); none of them was
   green, and each is recorded so the next reader starts from the fourth door rather than the first. What

  declares an object, not a merge patch).
- Raise `AppError` for anything that is not a field-validation failure; the 422 envelope for a bad
  body comes from B-04's `RequestValidationError` handler for free. Do not hand-build `detail`.
- Keep it simple: two handlers, one service function if the service file is touched at all.
