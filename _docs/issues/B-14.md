## Context

B-14 is the only issue whose subject is the test suite as a whole; B-05..B-13 each own a feature and
its module. Three things are true at this tree that the stub did not know. All three are measured.

**1. The one defect B-14 must own is real, and it is a host-clock bug, not a date flake.**
`backend/tests/test_admin_settings.py::test_the_settings_exemption_reaches_the_counters_the_contract_names`
(line 966) seeds the waitlist row the guest lookup must find with
`business_date=time.strftime("%Y-%m-%d")` (line 992) - the *host's local* calendar date - while the
app asks `business_date_for(branch, now)` (`backend/app/services/waitlist.py:337`), i.e.
`(branch-local now - business_day_cutoff_hour).date()`. They disagree exactly when branch-local time
falls between 00:00 and the cutoff hour; for the seeded Taipei branch (cutoff 4) that is
`16:00-20:00 UTC`, every day, forever. The Orchestrator's baseline saw it red at 23:46/00:06 UTC and
green at 07:37 UTC today. Re-measured here at `08dfebc`, one pytest run per zone, ~0.4 s each:

```
TZ=UTC                 2026-09-13 00:23 UTC   -> 1 passed
TZ=America/Sao_Paulo   2026-09-12 21:23 -03   -> 1 failed
TZ=Pacific/Kiritimati  2026-09-13 14:23 +14   -> 1 passed
TZ=Asia/Taipei         2026-09-13 08:23 CST   -> 1 passed
```

One test, one commit, four outcomes, one red. A CI runner at UTC-3 fails every merge gate in this
project, and a green that depends on `TZ` is not a gate. AC-2 owns it.

A correction stated plainly, because the dispatch brief carried an older reading of the mechanism: at
this tree the named test does **not** fail between 00:00 and 04:00 *Taipei*. Its `staff_headers()`
mints the JWT from `int(time.time())` and the test ends by asserting a `200` on the staff surface, so
freezing this test's clock invalidates its own token: a naive `@freeze_time("2026-09-11 02:00:00")`
pin measured `assert 401 == 200` at line 1009, and a pin whose *date* equals the host date stays
green - a date-only pin buys a false green. What actually breaks the test is a host whose **local
date** differs from the app's business date, which is what the four-zone table above produces. AC-2's
arms are written against that measured fact, and the failure the four-zone run prints is the same
`assert 401 == 200` reached by a different route (the lookup 404s, the surface it guards stops being
exempt). The consequence for this groom is none: the defect is real, load-bearing and owned here.

**2. The named test cannot see the day filter, and this groom says so out loud.** The obvious negative
control for a business-date AC - delete the filter line, watch something go red - does not work here,
and pretending otherwise is exactly the false green this project has been burned by. Measured twice in
this worktree:

- Deleting `if row.business_date != business_date_for(branch, now): continue` from `find_entry_by_tail`
  (`git diff --numstat` -> `0 2`) leaves the named test green (`1 passed`) and leaves the AC-5 probe
  green (`status=200`): with the filter gone, whatever day the row carries is accepted, so a broken
  app cannot be caught by a day-stamped row.
- Monkeypatching the lookup to ignore `business_date` entirely returns `200` from the AC-5 probe **and**
  keeps the named test green (`1 passed`), because that test's subject is the rate-limit exemption; the
  lookup is incidental plumbing to it.

So the honest split is: **AC-2** owns the named test's clock independence, whose belt *is* provable
(deleting its single `business_date=` line turns it red with `NOT NULL constraint failed:
waitlist_entries.business_date`), and **AC-5** owns the business-date rule through a probe whose two
arms are both demonstrated. AC-5 is green-reachable and red-honest, but it is not a filter test, and
its residual is named inside AC-5 and in Out of scope.
