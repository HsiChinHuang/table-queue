## Goal [SA]

The application refuses to boot with a JWT signing secret an attacker could know: empty, one of
the literals this repo publishes, or shorter than 32 characters. A deployment that copied the
shipped example fails loudly at startup instead of silently minting forgeable staff tokens, and a
regression test proves a token forged from the published literal is rejected while genuine tokens
keep working.

## Context [PM]

Why this task exists: HS256 means the configured secret is the *only* credential between an
anonymous caller and every staff/admin surface. `backend/app/dependencies.py:71` verifies with
`jwt.decode(token, settings.jwt_secret, algorithms=['HS256'])` and the login route signs with the
same string, so the HMAC key *is* the credential. The verification code itself is clean: D-1
point 4 checked algorithm pinning, no `alg:none` confusion, `exp`/`sub` required. The whole
weakness is the *quality of the configured value*, which nothing today constrains. The codebase
already owns the right pattern: `database_url` / `jwt_secret` / `staff_pin` are `Field(...)`
required, so a missing variable is a startup `ValidationError` in every environment, and
`backend/tests/test_config.py` pins that as a contract (B-01 AC-12). This issue extends that same
fail-closed-at-construction pattern from *presence* to *quality*.

- Related: #64 (T9, PIN integrity - same `Settings` object, same "no published credential" family;
  T9 owns `staff_pin`, this issue owns `jwt_secret`), #75 (T20, ENV fail-open), #76 (T21, logging
  configuration), #5 (B-01, fail-fast precedent), #2 (T2, the verifier this issue protects).
- Design: not a UI task, `_docs/design-system.md` not applicable.
- Plan: `_docs/plan.md`; the security statement this serves is `_docs/specs.md` section 15.

### Design decision (pinned by the ACs below)

**Decision: a quality gate at `Settings` construction that applies in EVERY environment, with no
bypass flag.** `jwt_secret` becomes a validated secret rather than a free-form string. A `Settings`
instance cannot be constructed unless `jwt_secret` (a) is a non-empty string after stripping
surrounding whitespace, (b) is at least 32 characters, and (c) is not one of the literals this repo
publishes (`change-me-in-production`, `test-secret-key`). The refusal is a `pydantic.ValidationError`
raised from a validator on the `Settings` model, i.e. the same class of failure and the same
`Field ... [type=..., ...]` message shape that a missing `JWT_SECRET` already produces today, so
`main.py`'s existing startup behaviour (exit non-zero with a pydantic error) is unchanged.

**Why not "enforce in production, warn in development".** Three reasons, heaviest first:

1. *Consistency with the existing fail-closed precedent.* An unset secret is already a startup
   `ValidationError` today in every environment - there is no environment where "missing secret"
   is tolerated with a warning. Making *strength* environment-conditional reintroduces exactly the
   shape audit A-3 / D-2 flagged for `ENV`: the permissive branch is the one you happen to be in.
   Presence and strength must fail the same way, or an operator learns to read only half of the
   startup error.
2. *A dev/test carve-out could not be asserted by any AC that matters.* `ENV=development` is the
   documented dev default (`config.py:36`, `.env.example:7`), so a gate that is lenient in
   `development` would be verified against a branch production never takes, and the shipped
   server boot - the thing A-1 actually compromised - would stay ungated.
3. *A documented escape hatch is the same failure mode as a documented default.* An
   `ALLOW_WEAK_JWT=true` would be copied into `.env` by the same operator profile that copied
   `.env.example`, and D-1's exploit precondition is literally "copied the example and did not
   replace the secret".

**Consequence SW must not dodge:** the repo's own harness boots on `JWT_SECRET=test-secret-key`
(15 chars *and* a published literal) in five test-side files (`backend/tests/conftest.py`,
`public_fixtures.py`, `test_public_board.py`, `test_public_waitlist.py`,
`test_staff_dashboard.py`, `test_staff_tables.py`). Strengthening that value is required, in
scope, and is what AC-6 pins; without it the suite cannot boot against its own code.

**Boundary of the gate.** This issue decides *quality of the configured value* and nothing else:
no entropy estimator, no cross-check against other `Settings` fields, no rotation, no `kid`, no
startup self-report banner. Each of those is named in Out of scope with a destination.

## Acceptance criteria [SA draft; PM refined]

Shared convention for every block below. Run from the repo root. `SECRET_OK len=<n>` with exit 0 is
the FIXED answer for a gate-compliant secret; a non-zero exit that names `jwt_secret` is the FIXED
answer for a weak candidate. Each block echoes its own verdict token (`PASS AC-<n>` /
`FAIL AC-<n> ...`) as its last line, asserts every count inside the same `if`, and removes its
scratch dir via `trap ... EXIT`. No block writes to the repo, to git, or to a database beside the
repo. Do not run these under `set -e` or `set -o pipefail`: the `| tail` / `| head` consumers would
yield a false FAIL exit code through SIGPIPE.

### AC-2

- [ ] **AC-2** The 32-character floor is enforced and pinned on both sides of the boundary: a
  31-character secret is refused, a secret of exactly 32 characters is accepted. Pass: the 31-char
  run exits non-zero AND names `jwt_secret`, AND the 32-char run exits 0 printing
  `SECRET_OK len=32`. (The accepted-side arm is what stops SW from "fixing" this by rejecting
  everything.)

```bash
W=${TMPDIR:-/tmp}/t10-ac2-$$; mkdir -p "$W"; trap 'rm -rf "$W"' EXIT
cd backend && set +e
probe() {
  env -u JWT_SECRET DATABASE_URL="sqlite:///$W/none.db" STAFF_PIN=0000 ENV=development \
    JWT_SECRET="$1" .venv/bin/python -c 'from app.config import Settings; s=Settings(_env_file=None); print("SECRET_OK len=%d" % len(s.jwt_secret))' 2>&1
}
s31=$(probe "$(printf 'a%.0s' $(seq 1 31))"); rc31=$?
s32=$(probe "$(printf 'a%.0s' $(seq 1 32))"); rc32=$?
cd ..
echo "len31: $(echo "$s31" | tail -1) rc=$rc31"
echo "len32: $(echo "$s32" | tail -1) rc=$rc32"
n31=$(echo "$s31" | grep -c "jwt_secret"); ok32=$(echo "$s32" | grep -c "SECRET_OK len=32")
if [ "$rc31" != "0" ] && [ "$n31" -ge 1 ] && [ "$rc32" = "0" ] && [ "$ok32" -ge 1 ]; then
  echo "PASS AC-2 floor enforced at 32"
else
  echo "FAIL AC-2 floor wrong n31=$n31 ok32=$ok32 rc31=$rc31 rc32=$rc32"
fi
```

   Measured today (RED at `5d23a3c`): `len31: SECRET_OK len=31 rc=0`, `len32: SECRET_OK len=32

### AC-5

- [ ] **AC-5** The repository stops shipping a usable secret. Pass requires all three: (i) neither
  `backend/.env.example`, `README.md` nor `_docs/deployment.md` contains `change-me-in-production`
  or `test-secret-key`; (ii) the `JWT_SECRET=` line in `backend/.env.example` is itself unusable -
  either commented out, or a placeholder whose value this issue's own gate would reject; (iii)
  `README.md` documents a generation command containing `secrets.token_urlsafe` (D-1's fix
  direction), so an operator is never handed a value in place of an instruction.

```bash
set +e
hits=$(grep -RniE "change-me-in-production|test-secret-key" backend/.env.example README.md _docs/deployment.md 2>&1 | grep -v "/.venv/" | wc -l | tr -d ' ')
line=$(grep -E "^[[:space:]]*#?[[:space:]]*JWT_SECRET=.*$" backend/.env.example | head -1)
echo "example line: ${line:-<absent>}"
if echo "$line" | grep -q "^[[:space:]]*#"; then unusable=1
  elif echo "x$line" | grep -Eqi "REPLACE|YOUR_|CHANGE|__|PLACEHOLDER"; then unusable=1
  else unusable=0; fi
val=$(echo "$line" | sed 's/^[^=]*=//')
if [ "$unusable" = "0" ]; then
```

### AC-6

- [ ] **AC-6** The test harness itself no longer boots on a secret that this issue's gate rejects,
  and the whole backend suite stays green on a gate-compliant secret. Pass requires all three,
  asserted in one `if`: at least one `JWT_SECRET` string literal is actually configured in
  `backend/tests/**.py` (`total>=1`, so an AC that silently stopped matching cannot read green),
  zero of those literals is below the gate (`bad=0`: shorter than 32 chars, or equal to
  `change-me-in-production` / `test-secret-key`), and `pytest` exits 0.

  This is the AC that makes the design decision's consequence enforceable: at base the harness sets
  `test-secret-key` (6 sites), `'test'` (`backend/tests/test_schemas.py:226`) and `"x"`
  (`backend/tests/_atomicity_probe.py:32`), all of which the fixed gate rejects, so the suite
  cannot even import `app.main` after AC-1..AC-4 land unless these values are strengthened.
  `total>=1` is the self-falsification guard for this AC.

```bash
set +e
W=${TMPDIR:-/tmp}/t10-ac6-$$; mkdir -p "$W"; trap 'rm -rf "$W"' EXIT
mapfile -t lits < <(grep -rhi --include="*.py" -oE 'JWT_SECRET["'"'"'][[:space:]]*,[[:space:]]*["'"'"'][A-Za-z0-9._-]+["'"'"']' backend/tests)
total=${#lits[@]}
bad=0
for x in "${lits[@]}"; do
  v=$(printf '%s\n' "$x" | sed -E 's/.*,[[:space:]]*//; s/^["'"'"']//; s/["'"'"']$//')
  L=${#v}
  if [ "$L" -lt 32 ] || [ "$v" = "change-me-in-production" ] || [ "$v" = "test-secret-key" ]; then bad=$((bad+1)); fi
done
echo "harness JWT_SECRET literals: total=$total below-gate=$bad"
cd backend && timeout 600 .venv/bin/python -m pytest -q --basetemp="$W/pt" >"$W/pt.out" 2>&1; rcp=$?; cd ..
tail -1 "$W/pt.out"
if [ "$total" -ge 1 ] && [ "$bad" = "0" ] && [ "$rcp" = "0" ]; then

  echo "FAIL AC-6 total=$total bad=$bad pytest_rc=$rcp"
fi
```

   Measured today (RED at `5d23a3c`): `harness JWT_SECRET literals: total=9 below-gate=9`, suite

### AC-7

- [ ] **AC-7** Forged-token regression: the A-1 / D-1 exploit, pinned. Two servers are booted and
  the same offline-minted HS256 token (signed with the published literal
  `change-me-in-production`, never issued by the app) is replayed against both. Pass requires, in
  one `if`: `401` for the forged token against a server on a random compliant secret (control for
  "the verifier still works"), `200` for a genuine token minted from that server's real secret
  (control for "the gate did not break auth"), AND `401` for the forged token against a server that
  itself runs the published literal - the third arm is the one that is RED at base and is what
  makes this AC the exploit pin rather than a tautology.

```bash
set +e

from jose import jwt
print(jwt.encode({"sub":"staff","role":"staff","iat":int(time.time()),"exp":int(time.time())+3600}, sys.argv[1], "HS256"))

cd backend
env -u ENV -u CORS_ORIGINS DATABASE_URL="sqlite:///$W/srv.db" JWT_SECRET="$REAL" STAFF_PIN=0000 \
  timeout 90 .venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8310 >"$W/srv.log" 2>&1 &
p1=$!
cd ..
for i in $(seq 1 60); do curl -sf http://127.0.0.1:8310/health >/dev/null 2>&1 && break; sleep 0.5; done
FORGED=$(.venv/bin/python -c "$MINT" change-me-in-production 2>/dev/null | tail -1)
GENUINE=$(.venv/bin/python -c "$MINT" "$REAL" 2>/dev/null | tail -1)
f=$(curl -s -o /dev/null -w '%{http_code}' -H "Authorization: Bearer $FORGED" http://127.0.0.1:8310/api/v1/staff/dashboard)
g=$(curl -s -o /dev/null -w '%{http_code}' -H "Authorization: Bearer $GENUINE" http://127.0.0.1:8310/api/v1/staff/dashboard)
kill $p1 2>/dev/null; wait $p1 2>/dev/null
echo "REAL-SECRET SERVER: FORGED=$f GENUINE=$g"
cd backend
env -u ENV -u CORS_ORIGINS DATABASE_URL="sqlite:///$W/srv2.db" JWT_SECRET=change-me-in-production STAFF_PIN=0000 \

cd ..
for i in $(seq 1 60); do curl -sf http://127.0.0.1:8312/health >/dev/null 2>&1 && break; sleep 0.5; done

kill $p2 2>/dev/null; wait $p2 2>/dev/null
cd ..
echo "PUBLISHED-LITERAL SERVER: FORGED=$f2"
if [ "$f" = "401" ] && [ "$g" = "200" ] && [ "$f2" = "401" ]; then
  echo "PASS AC-7 forged token from published literal rejected on both servers"
else
  echo "FAIL AC-7 forged=$f genuine=$g forged-on-published=$f2"
fi
```

   Measured today (RED at `5d23a3c`): `REAL-SECRET SERVER: FORGED=401 GENUINE=200` (both controls

### AC-8

- [ ] **AC-8** No-regression pin (the "do not break the door you just locked" arm): with a
  gate-compliant secret, real authentication still works end to end. Three arms, one `if`: (i)
  `POST /api/v1/auth/login` with the configured `STAFF_PIN` returns `200` and a non-empty
  `access_token`; (ii) that server-issued token gets `200` on `/api/v1/staff/dashboard`, and no
  bearer at all gets `401` (the existing unauthorized contract, `AUTH_TOKEN_EXPIRED` envelope);
  (iii) `pytest backend/tests/test_config.py backend/tests/test_auth.py
  backend/tests/test_dependencies.py` exits 0, so the fail-fast contract B-01 AC-12 pins and the
  verifier's own tests survive the new validator. Pass: login 200 AND token-auth 200 AND bare 401
  AND pytest 0.

  **Expected state: GREEN at base and required GREEN after the fix.** Unlike AC-1..AC-7 this is not
  a finding pin; it is the property that must not regress, and it is the reason AC-6's harness
  strengthening is mandatory rather than optional.
