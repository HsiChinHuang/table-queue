## Metadata

- Platform issue: **31**
- State: `groomed`
- Role: SW (backend)
- Contract sources: `_docs/specs.md` section 3 (Auth Model), section 11 (error table),
  `_docs/openapi.yaml` (`/api/v1/auth/login`, `/api/v1/auth/change-pin`, `StaffLoginRequest`,
  `StaffLoginResponse`, `ChangePinRequest`), `_docs/deployment.md` (login rate limit 5/minute)

## Goal

Implement `POST /api/v1/auth/login` and `POST /api/v1/auth/change-pin` in
`backend/app/routers/auth.py` and mount the router, so staff exchange the shared PIN for an
HS256 JWT and can rotate that PIN.

## Context

`app/dependencies.py` (B-04) already provides `Staff` (a `Depends(get_current_staff)`
annotation), `bearer_scheme` with `auto_error=False`, and `AppError`/`register_error_handlers`
(B-04) which turn any raised `AppError` into the `{"error":{"code","message","details"}}`
envelope. `app/schemas.py` (B-03) owns every request/response model. This issue writes only the
route layer plus its tests, and it is the first issue to mount a router on the app.

Two rulings fix contract conflicts before implementation starts:

- **R-B05-1 (error code on 429).** The Platform Issue bullet says `AUTH_RATE_LIMITED`, but
  `_docs/specs.md` section 11 lists `AUTH_RATE_LIMITED` under "Codes outside the API contract"
  and says login's 429 resolves through `components.responses.RateLimited` to `RATE_LIMITED`.
  `openapi.yaml` is the contract of record, so the limiter must emit `RATE_LIMITED` and no code
  may invent `AUTH_RATE_LIMITED`. AC-12 asserts `RATE_LIMITED`.
- **R-B05-2 (`expires_in` is derived).** `expires_in` must equal `settings.jwt_expire_hours * 3600`
  (12 hours = 43200 by default). The ACs therefore run with `JWT_EXPIRE_HOURS=3` and assert 10800,
  so a hard-coded 43200 cannot pass.

## Implementation notes

- Create `backend/app/routers/__init__.py` and put both routes in `backend/app/routers/auth.py`
  with a module-level `router = APIRouter()`. Mounting it in `backend/app/main.py` is the one
  allowed edit outside the routers package: `app.include_router(auth_router)` after
  `register_error_handlers(app)`, plus the import. Nothing else in `main.py` changes (its lifespan
  and `bootstrap_defaults` belong to B-01, and its middleware/limiter wiring to B-04).
- Reuse B-04: raise `AppError('AUTH_INVALID_PIN')` for bad credentials, let
  `app/dependencies.get_current_staff` (or the exported `Staff` alias) guard change-pin, and let
  the registered handlers render envelopes. Do not build a second error shape, and do not catch
  `RateLimitExceeded` yourself - B-04's handler already maps it to 429 `RATE_LIMITED`.
- Rate limit: decorate login with `@limiter.limit("5/minute")` using the `limiter` object that
  `app.main` exports (the same instance stored on `app.state.limiter`), and give the handler a
  `request: Request` parameter - slowapi raises at import time without one, and FastAPI matches the
  first registered route so an extra probe route must not be added to the app.
- PIN verification order: if `Settings.staff_pin_hash` is a non-empty string, `bcrypt.checkpw`
  against it; otherwise compare against `settings.staff_pin` (`STAFF_PIN` env). AC-3 exists because
  `bootstrap_defaults` inserts `staff_pin_hash = null`.
- Build the token with `jose.jwt.encode({...}, settings.jwt_secret, algorithm="HS256")`, `exp =
  now + settings.jwt_expire_hours * 3600`, and return the same number as `expires_in` (AC-12
  cross-checks `exp - iat == expires_in`, so compute both from one value).
- Import request/response models from `app/schemas` (B-03 already defines all three) and declare
  `response_model=StaffLoginResponse` on login, `status_code=204` on change-pin. AC-13 fails the
  issue if the router defines its own pydantic models.
- `new_pin == current_pin` and `new_pin != confirm_new_pin` must be rejected as 422
  `VALIDATION_ERROR` (AC-9). `app/schemas.ChangePinRequest` has no cross-field validator, so raise
  `RequestValidationError`-equivalent 422 through the existing handler path - the simplest compliant
  route is a router-level check that raises `AppError` configured for 422 `VALIDATION_ERROR`... which
  is exactly what B-04's `AppError(code, status_code=422)` supports. Do not add validators to
  `app/schemas.py` (B-03's file) and do not relax pyproject lint rules.
- **`Staff` is already an `Annotated` alias** (`app/dependencies.py:66` =
  `Annotated[dict[str, str], Depends(get_current_staff)]`). Use `staff: Staff` in the route
  signature. Writing `staff: Annotated[dict, Depends(Staff)]` makes FastAPI treat the returned dict
  as a request-body model and change-pin answers **422 before authentication runs**, so every 401 in
  AC-7 becomes unreachable (R-B05-12).
- **AC-7 requires the router to enforce the staff claim.** `get_current_staff` validates signature,
  expiry and `sub` presence but accepts any `sub`, so a guest token signed with the real secret would
  otherwise pass. Raise `AppError('AUTH_TOKEN_EXPIRED')` when `staff["sub"] != "staff"` (specs fixes
  code+status only; openapi fixes only `code: AUTH_INVALID_PIN`, and specs does not fix the human
  message, so tests must never assert exact message text - R-B05-11).
- **Keep `token_type` out of keyword arguments.** Ruff (same config that gates AC-14) flags S106 for
  `token_type="bearer"` in any call and S105 for `TOKEN_TYPE = "bearer"`, while dict literals are
  clean: `return {"access_token": token, "token_type": "bearer", "expires_in": expires_in}` passes
  and `response_model=StaffLoginResponse` still validates/shapes it. The same applies to
  `access_token=`.
- **Login rate limiting is process-global in tests.** `limiter._storage.reset()` does not undo a
  consumed burst, but `limiter.enabled = False` does suppress limiting. AC blocks each run in their
  own process so they are unaffected; `backend/tests/conftest.py` needs an autouse fixture that
  disables the limiter, and the one rate-limit test re-enables it (R-B05-6).
- Success path for change-pin: write the new bcrypt hash into `Settings.staff_pin_hash` for the
  single settings row, commit, return 204 with no body (AC-8 proves the write with a fresh process).
- AC probes create their own `Settings` row because login needs one; the route must read settings by
  querying the table, not by assuming a row exists, and must not 500 when `settings` is empty.
