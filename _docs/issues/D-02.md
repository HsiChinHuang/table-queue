**4. The transaction boxes have a measurable form, and it is not the one the stub implies. Measured.**
The shipped write paths do not open nested transactions: they write both rows on one session and issue
**one** `commit()` (`services/staff_waitlist.py::seat_entry` `:655-669`, `_close_entry` `:692-699`,
`reorder` `:945-955`; `services/tables.py::release_table` `:487-496`), and specs section 14 says exactly
that ("the release writes both halves on one session with one `commit()`"). "Tests cover transaction
rollback on error" is therefore observable as **both-or-neither**: break the commit and prove the database
moved nobody. That is reachable without touching product code, by listening to SQLAlchemy 2.0's own
`commit` engine event (`event.listens_for(engine, "commit")`, which fires once per commit with the DBAPI
connection) and raising from it. This groom measured it in a throwaway module (`_pm/mut_test_db_atomic.py`,
489 lines, 12 cases) and measured the numbers AC-1 and AC-3 pin: the release path's commit count on this
engine is **1** (`RELEASE_COMMITS=1`), a broken release commit answers **500** and leaves the party
`SEATED` with `closed_at IS NULL`, a broken seat commit answers **500** with the *objects* reading
`SEATED/OCCUPIED` while the **file** keeps `WAITING/AVAILABLE`, and a broken reorder commit answers **500**
having flushed only its **first** `sort_order` - which the rollback undid, so every position reads back
unchanged (`test_reorder_commit_failure_moves_nobody PASSED`). Two further measurements bound the
mechanism: arming the listener **unconditionally** makes every write in the suite revert to its
pre-request value (so an AC file must arm **by count** and restore in a `finally`, or it manufactures a
false green), and `engine.dispose()` is not the mechanism (D-01 Out of scope 4: no shutdown path,
`poolclass=NullPool`).
**Three facts that constrain how a failure test may be written.** (a) FK enforcement is off by default
(`PRAGMA foreign_keys` -> `0`) and `waitlist_entries.table_id` is a FK to `tables` with neither

row points at it does **not** fail here - the child keeps a dangling id. (b) `uq_queue_seq` bites
