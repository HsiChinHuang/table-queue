## Decision (PM, T20 groom round 1)

Four questions had to be settled before any AC could be falsifiable. They are settled here, and the
ACs pin the chosen *behaviour*, never the chosen implementation.

**D-1 - explicit-ENV-required, not default-production.** `Settings` refuses construction when `ENV`
is absent and when it carries a value outside the allow-list `development | test | production`.
Chosen over `default="production"` for three reasons. (1) Precedent: this same class already refuses
construction for a weak `jwt_secret` (T10's quality gate is on main), and A-1's fix direction asks for
the two in one breath ("require an explicit `ENV` value ... so 'unset' is never a production state").
(2) A `production` default is only safe for today's three consumers; the next
`if settings.env == "development"` (docs surface per A-10/D-10, traceback verbosity per D-3, some
future debug route) re-opens exactly this hole with a default that now lies the other way and a store
that silently behaves as though nothing was defaulted. Fail-fast is operator-visible at boot; a
silent default is invisible in precisely the way the audit calls the defect. (3) The AC pair is
stronger: with a required field, AC-1's refusal clauses and AC-3's "never answers" clause measure one
mechanism, whereas a `production` default would leave every guard still keyed on a value nobody chose.
The cost is stated honestly in Constraints: every run command that omits `ENV` breaks loudly, which is
the point, and it is a documented contract change (`README.md:275` lists `ENV` as optional with
default `development`).

A `settings.env_explicit`-style companion attribute is *not* the mechanism and no AC may require one:
pydantic-settings v2 folds `os.environ` and constructor kwargs into one validated namespace, so a
default-applied field and a value that came from `ENV=...` are indistinguishable on the instance.
Measured at base with the probes named in Groom baseline: `model_fields_set` on an instance built with
no `env` kwarg and no `ENV` variable is `['database_url','jwt_secret','staff_pin']` - no `env` - while
with `ENV=production` exported it becomes `['database_url','env','jwt_secret','staff_pin']`. So the
only reliable signal is presence at *construction* time, which is why the check is a validator that
fires on a value the caller never supplied rather than an attribute reporting where a value came from.

**D-2 - the reset guard keeps reading the resolved setting, and only `development` passes.**
`get_settings().env` stays the read seam (B-12's contract, and `test_admin_reset.py:143` documents
why), and the comparison stays an equality against the single permissive value: `development` passes,
`test` and `production` answer 403, anything else never reaches the handler because D-1 refused the
boot. AC-2 additionally pins that the endpoint does not answer 204 for a process whose environment
merely *omitted* the word. No second opt-in variable (`ALLOW_DATA_RESET`) is required here: a second
flag whose default is also a default is the same class of bug one level down, and #78 (T23) owns the
seed-literal half of that destructive surface. If a second gate is ever added it must not weaken the
env check.

**D-3 - `echo` is decoupled from `env` and defaults off; T21 owns the logger, T20 owns the
derivation.** Neither `backend/app/database.py:42` nor `backend/app/seed.py:35` may compute echo from
`settings.env`. The field is named `SQL_ECHO` (AC-5 pins the name, because an AC cannot assert against
a name it does not state), and the hard rule is that echo is off unless it is explicitly asked for.
The split, stated once: **T20 owns the echo default coupling only** - the `echo=` keyword on those two
`create_engine` calls and the settings field that replaces the `env ==` expression. **T21 owns logger
configuration** - handler, formatter, level, uvicorn's duplicate ASGI traceback, traceback verbosity,
and D-3's `[SQL: ...]`-inside-an-exception-message leak, which travels the logging path and is not an
`echo=` leak. T20 adds no `log_config` and no handler.

**D-4 - `/health` keeps its `env` field and must never name an environment the operator did not
choose.** The field stays: `test_health.py` asserts its presence, and A-11's trim-to-`{"status":"ok"}`
proposal is out of scope here. Under D-1 there is no implicit value left to report, so AC-3 pins the
externally visible half: a process booted with `ENV=production` reports exactly `production`, a
process booted with no `ENV` never answers at all, and the field never carries an off-list value.

## Acceptance criteria

Six blocks, each runnable on its own from the repo root of the tree under test. Do not run them under
`set -e` or `set -o pipefail`, and never pipe one into a truncating consumer such as `head`: a
state-changing block that is SIGPIPEd yields a false FAIL, and rc is not the verdict here in either
direction - the verdict TOKEN is (`PASS AC-<n>:` for the whole-AC line, `FAIL AC-<n> <clause>: <what
was measured>` per clause). This is a FIX issue, so every block is expected RED at the groom base
through at least one of its own clauses, and each block's `Measured today:` line carries the raw red
output plus the mutation-falsification arms that were actually measured.

Three conventions that are load-bearing, all measured rather than assumed:

- **Which tree gets imported is stated, not inherited.** `backend/.venv` is a symlink onto the suite
  venv, whose `pyvenv.cfg` makes a child process resolve `sys.path[0]` to the *main checkout's*
  `backend/`, so a block relying on the ambient `PYTHONPATH` can measure another tree and never
  notice. The blocks export `T20PROBEPATH=$PWD/backend` and hand that value down as the child's
  `PYTHONPATH`; AC-5 additionally prints `DB_FILE:`, the resolved `app/database.py` path, so its
  measurement names the tree it came from. AC-8 re-checks those paths.
- **Scratch.** Everything a block writes goes under `_t20_scratch` - its SQLite files and its staged
  probes included - and the directory is removed on the way out; AC-8 asserts the tree is clean
  afterwards. Run the blocks one at a time: two blocks booting the same store fight over it.
- **The environment is a process fact.** `Settings` is `lru_cache`d and both `app.main` and
  `app.database` read it at import time, so every block that measures a boot-time decision does it in
  a fresh subprocess with an environment it builds itself (`ENV` present, or deliberately absent),
  never by monkeypatching a module global. The rebind-the-seam shape is already covered by
  `backend/tests/test_admin_reset.py`, and repeating it here would pin a different fact than the one
  this issue is about.

- [ ] **AC-1** `ENV` is required and validated at construction: a process with no `ENV` set, with
`ENV` set but empty, or with `ENV` outside the allow-list `development | test | production` never
boots the application at all (no silent `development`), while each of the three allowed values boots
and `/health` reports it verbatim.

Pass: the block prints a line beginning `PASS AC-1:`. Its six clauses are named in its own output
(`p_absent_refused`, `p_blank_refused`, `p_staging_refused`, `p_dev_boots`, `p_test_boots`,
`p_prod_boots`) so QA can see which half moved. The three refusal clauses are this AC's red half at
the groom base; the three boot clauses are not-breaking pins, expected GREEN before and after the fix,
because requiring the variable must not break the environments that do name themselves.

Mutation-falsification design, each one edit and each a *different* wrong answer. (a) Flip the default
to `test` *and* add the allow-list (`env: Literal[...] = Field(default="test")`, validator deleted) -
the single edit most likely to be offered as "the fail-open is closed": measured against that tree the
block prints `FAIL AC-1 p_absent_refused: ... saw: HEALTH: ... "env":"test"` and nothing else, so AC-1
is still not satisfied while every other signal looks healthy, and a block that measured only boot
behaviour would wrongly pass. (b) Add the allow-list without the
requirement (`env: Literal["development","test","production"] = Field(default="development")`):
measured at base, `p_blank_refused` and `p_staging_refused` go PASS and `p_absent_refused` alone stays
FAIL, so a fix must refuse the *absence* and not merely the bad value. (c) The reverse mutant - a
validator that rejects an absent `ENV` but admits `staging` - is caught by `p_staging_refused`, which
is why that arm is a refusal clause.
