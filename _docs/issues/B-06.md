## Goal

Serve the five guest-facing operations with no auth: public branch info, the public board, joining
the waitlist, checking a waitlist status, and cancelling one - so a guest on a QR-code link can join,
watch and leave a queue, and so no guest response ever leaks a full name or a full phone number.

## Context

Dependencies B-02/B-03/B-04 are merged, so the route layer is written against existing
infrastructure instead of being rebuilt here:

- `app/models.py` (B-02) owns `Restaurant`, `Branch`, `Table`, `WaitlistEntry`, `Settings`.
  `WaitlistEntry` has **no** `status_token` column; see R-B06-4.
- `app/schemas.py` (B-03) owns `JoinWaitlistRequest` (with the Taiwan phone validator),
  `CancelWaitlistRequest`, `WaitlistEntryResponse`, `WaitlistStatusResponse`, `PublicBranchResponse`,
  `BoardResponse`. The route layer imports these and defines none of its own.
- `app/errors.py` and `app/dependencies.py` (B-04) provide `AppError` and `ERROR_CODES` (parsed from
  `_docs/specs.md` section 11), the `VALIDATION_ERROR` 422 handler, the `RATE_LIMITED` 429 handler,
  and `app.state.limiter` (slowapi). Raise `AppError`; never hand-build an error envelope.
- `app/main.py` mounts no router yet, so this issue also registers `public.router`.

Four rulings close contract gaps before implementation starts:

- **R-B06-1 (board `recent_calls` cap is 3).** Neither `_docs/specs.md` nor `_docs/openapi.yaml`
  caps `recent_calls`; the only source in the repo is this issue's own requirement, and the
  `BoardResponse` example carries two items, which is compatible with any cap of 2 or more. This
  number is the only place in the repo that states it, so it is stated plainly rather than cited:
  `recent_calls` holds at most the 3 most recent entries that have left `WAITING`, newest first.
  AC-6 measures the cap by producing 4.
- **R-B06-2 (duplicate phone is scoped to the branch and day).** `_docs/specs.md` section 7 says
  "Phone must be unique among active statuses (WAITING, CALLED, SEATED)" without naming a scope, and
  every other waitlist rule in the document is branch-scoped. Uniqueness is therefore scoped to one
  branch and one `business_date`.
- **R-B06-3 (the `waiting_ahead` formula is written down).** The SA prose said `waiting_ahead x
  avg_seat_minutes` without defining `waiting_ahead`, and neither spec document defines it.
  `waiting_ahead` is the count of `WAITING` entries in the same branch and `business_date` whose
  `sort_order` is strictly lower, and the estimate is `waiting_ahead * avg_seat_minutes` read from
  `Settings`. AC-9 encodes it with three entries ahead carrying party sizes 2, 6 and 1, so an
  implementation that weights by party size cannot pass.
- **R-B06-4 (`status_token` has no storage).** `_docs/specs.md` section 6 and
  `WaitlistEntryResponse` both carry `status_token`, but section 6 lists no `status_token` column and
  `models.py` (B-02, merged) has none, so the token is derived deterministically from stored columns:
  SHA-256 over `entry.id | entry.phone | entry.created_at.isoformat()`, first 16 hex characters.
  That keeps the `phone_last3` credential AC-10 checks from becoming a tautology (a random token
  stored beside the phone would make the two credentials the same secret), and it is verifiable by
  recomputation in AC-8. B-02 is merged and out of this issue's scope, so no column is added; if a
  later issue wants revocable tokens, that is #43 (D-01) territory.

  canonical class `[\u3400-\u9fff\u3000-\u303f\uff00-\uffef]` is NOT used here because it counts
  `\uff0b` (fullwidth plus) and other benign fullwidth forms as CJK, so a contract example dialled
  with U+FF0B in front of `886-900-000-001` - a `+886` country prefix is a
  plausible future example in a Taiwan-format issue - would false-positive. Measured on a one-character string: canonical 1, CJK_PIN 0.

Six numbers, both classes over the three documents (the counts are of matching characters; the
non-ASCII inventory is what makes each count explicable). Measured today, this tree:

    file                      non-ASCII code points found            canonical class  CJK_PIN
    _docs/specs.md            U+2013, U+2014, U+2192, U+2194           0                0
    _docs/openapi.yaml        U+2013, U+2014                           0                0
    _docs/issues/B-06.md      (none - zero non-ASCII characters)       0                0

None of U+2013 en dash, U+2014 em dash, U+2192 rightwards arrow or U+2194 left right arrow is in
either class, which is why both read 0 on all three files. Mutation proof (scratch copies under
`/tmp`, no repo file touched): a copy of `test_public_board.py` carrying the escape-written
CJK run above counts canonical 3, CJK_PIN 2 and the arm prints `FAIL AC-15[1-schema]: CJK in ...`; a copy of this issue
file carrying a lone U+FF0C counts canonical 1, CJK_PIN 0 - the narrowed class does NOT fire on a lone
fullwidth comma, which is the known cost of the narrowing, and that residue is why CJK_PIN keeps its
ideograph half as a standalone alternative: add the kana around it and CJK_PIN fires (2). A lone
U+FF0B counts canonical 1, CJK_PIN 0, which is the false positive the narrowing removes.

  spelling (bare `phone`, `full_phone`, `phone_full`, `phone_last4`, `phone_last_4`, `phone_last_3`)

- **`phone_masked` delimiter and star policy stays unpinned (open gap, deliberate).** The contract's
  one example is `0900-***-001` for the input `0900-000-001`, and the delivered implementation
  reproduces it. Nothing in `_docs/specs.md`, `_docs/openapi.yaml` or this issue fixes the delimiter
  policy, the star count or the head-keep split for any other input, and the guest status answer
  deliberately returns a different, compact form (`***014`) because that answer can be fetched with
  the last three digits alone. Pinning this needs a contract ruling, not an AC edit, so it is
  recorded here and left to the SA rather than frozen into an AC that would then outlive its
  justification.
- Do not add a `status_token` column or field to `WaitlistEntry`, do not add a path that is not in
  `_docs/openapi.yaml`, and do not add a dependency to `pyproject.toml` (freezegun, bcrypt, slowapi
  and python-jose are already installed).
- Do not over-engineer: no notification dispatch, no websockets, no Redis, no new table, no cache.
- **AC-14 rate limiting: how to wire it so the AC actually measures something (newly earned from
  B-05's gate at `957ff1f`).** The shared limiter is NOT the missing piece: `limiter =
  Limiter(key_func=get_remote_address)`, `app.state.limiter = limiter` and
  `app.add_middleware(SlowAPIMiddleware)` already exist in `backend/app/main.py` on main (`69384b7`),
  verified by grep on a clean `git archive 28ba24ca | tar -x` export. What is missing is the route
  wrapper, and slowapi does not allow attaching it after the fact: `@router.post(...)` / `@router.get(...)`
  stores the ORIGINAL function object in the route, so a later `handler = limiter.limit("10/minute")(handler)`
  rebinds only the module global and the registered route stays unwrapped - the AC then passes for the
  wrong reason or fails for the wrong reason. Register the route WITH the wrapped handler, inside
  `configure_limiter` (the same place B-05 registers the auth router): for example
  `router.post("/api/v1/waitlist", status_code=201)(limiter.limit("10/minute")(join_waitlist))`, and
  reuse the module-level `limiter` that `app.state.limiter` already points at - never a second
  `Limiter(...)` instance in `public.py`, which AC-14 already fails on sight.
- **What AC-14 honestly pins, and what it does not.** Its probe asserts the 11th lookup in the window
  is 429 `RATE_LIMITED` after ten unblocked ones, and that the limiter is the shared
  `app.state.limiter`. It does NOT pin the string `10/minute` against `10/hour` or `10/day`: a
  slowapi fixed-window counter cannot be distinguished from inside a single test window, because
  every request in a frozen window falls in the same bucket regardless of the unit. Measured on B-05:
  `5/minute` and `5/hour` both produce `401,401,401,401,401,429`, and 30 rapid attempts produce 30x
  `429`. So AC-14 proves "a limit exists on the shared limiter, is at least 10, and is exceeded at
  the 11th call"; a `20/minute` or `10/hour` implementation would also pass it. Implement `10/minute`
  because that is the contract value in `_docs/specs.md`, not because the AC can tell.
  Consequence for the SW: if you change the limit string or drop the wrapper and AC-14 stays green,
  the AC is not measuring your change - check the wrapper registration directly.
