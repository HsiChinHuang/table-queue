## Goal

`backend/app/main.py:bootstrap_defaults` inserts the default settings row with a raw `text()` INSERT
that omits `sound_enabled_default`. B-02 added that column as `nullable=False` with a SQLAlchemy
**Python-side** `default=True`, and a Python-side default never applies to a raw SQL statement. So on
a database whose schema came from `Base.metadata.create_all`, the bootstrap INSERT dies with
`IntegrityError: NOT NULL constraint failed: settings.sound_enabled_default`.

Fix the INSERT so a fresh schema bootstraps a settings row with `sound_enabled_default` set, and pin
that behaviour with a test.

## Context

Reproduced independently on `origin/main` (`c13931e`) in a scratch clone on ext4:

    BUG REPRODUCED -> IntegrityError (sqlite3.IntegrityError) NOT NULL constraint failed:
    settings.sound_enabled_default

`PIPELINE.md` (`.tq-orchestrator/`, around the B-13 entry) already records this mismatch and defers it
to `D-INT-3` — an identifier that names no Platform Issue and no file under `_docs/issues/`. That
deferral is a dead end; this issue supersedes it.

The bug does not surface in the current test suite because no AC or test calls `bootstrap_defaults`
against a schema created from `models.py`; B-13's seed path builds its own row and sets the column
explicitly. It surfaces on any real first boot of a fresh database.

## Test requirements

- Add a regression test under `backend/tests/` that calls `bootstrap_defaults` against a schema built
  from `Base.metadata.create_all` and asserts the settings row exists with `sound_enabled_default`
  true. A test that only greps the SQL string is not acceptable — AC-1/2/3 are behavioural for that
  reason.
- The test must not depend on `backend/.env` or on env vars set by hand; the conftest env defaults are
  the contract.

## Implementation notes

- Two changes are required, not one. Probe-proven: applying only the INSERT fix leaves AC-5 red with
  `sqlite3.OperationalError: table settings has no column named sound_enabled_default`, because
  `backend/tests/test_startup.py:create_test_tables` hand-writes a `settings` table without the column.
  1. Add `sound_enabled_default` to the column list and `true` at the matching position of the `VALUES`
     tuple in `bootstrap_defaults`. Keep every line inside 100 columns (ruff E501).
  2. Replace the body of `create_test_tables` with `Base.metadata.create_all(engine)` (import
     `app.models` for its side effect; keep the import order ruff I001 wants, `import app.models`
     before `from app.database import Base`). Delete the hand-written `CREATE TABLE` statements.
- Verified throwaway probe on a scratch clone at `origin/main`: both edits together give
  `55 passed` (same count as before the change) and `All checks passed!`. Probe preserved under
  `/home/te/tq/preserve/b15-probe/`.
- Do not touch `models.py` (AC-4), `seed.py` (B-13 owns it, and it already sets the column explicitly),
  or `pyproject.toml`.
- `TestClient(app)` on a fresh sqlite file leaves a database with NO tables (PIPELINE, B-13 entry), so
  build the schema in the test rather than leaning on the lifespan.

## Why the test suite never caught this

`backend/tests/test_startup.py:create_test_tables` hand-writes
`CREATE TABLE settings (id, branch_id, hold_minutes, avg_seat_minutes, queue_prefix,
is_waitlist_open, notification_templates, staff_pin_hash, created_at, updated_at)` — it omits the
`sound_enabled_default` column that B-02 added to `models.py`. A hand-written table with no such
column has no NOT NULL constraint to violate, so the bootstrap INSERT succeeds and the existing
startup tests stay green while a real database (built from `models.py`) cannot be bootstrapped at
all. The new test must build its schema with `Base.metadata.create_all`, never with a hand-written
`CREATE TABLE`.
