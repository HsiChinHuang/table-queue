## Goal

nothing about the probe's **output** changes on the green path: same measurement line, same

## Context

### The defect, in the shipped text

`_docs/issues/B-05.md` AC-3's block computes one flag and prints two lines (shipped `main` at
`6424460`, lines 150-153 of that file):

```python
ok = good.status_code == 200 and bad.status_code == 401 and bad.json().get('error', {}).get('code') == 'AUTH_INVALID_PIN'
print(('FAIL AC-3: ' if not ok else '') + 'good=' + str(good.status_code) + ' bad=' + str(bad.status_code) + ' ' + str(bad.json())[:120])
print('PASS AC-3: NULL staff_pin_hash falls back to STAFF_PIN, wrong PIN still 401 AUTH_INVALID_PIN' if ok else 'FAIL AC-3: STAFF_PIN fallback not implemented as specified')
```

That is **one** condition deciding **both** verdict routings. So the AC cannot say "the measurement
line is wrong" and "the fallback behaviour is wrong" as two different findings, and its consumer
cannot decide its two arms independently either. The split this issue specifies preserves every
assertion and changes only verdict routing:

- (a) *measured*: the probe prints the measurement line, byte for byte, and that line carries a
  `FAIL AC-3: ` prefix only when the measured shape is broken. Verdict id `fail-ac-three-measured`.
- (b) *behaviour*: the NULL `staff_pin_hash` falls back to `STAFF_PIN`, that PIN authenticates, any
  other gets 401 `AUTH_INVALID_PIN`. Verdict id `fail-ac-three-behaviour`.

### Why this is a three-way split, not two conditions (measured, not asserted)

`_docs/testing.md` rule 1 (shipped) is literal: "a block must print exactly one of `PASS AC-n: ...`
or `FAIL AC-n: ...`". A line that carried both tokens is what the D-06 round-b note calls the
runner's `FAIL,PASS` artifact: runacs collects tokens line-wise, so that block can never be
unambiguously decided. That rule, not aesthetics, forces three printed verdicts for two conditions,
because the measurement line's prefix is driven by (a) while the behaviour verdict is driven by (b):
under a two-condition split with a *single* behaviour verdict line, the red-behaviour/green-measured
case prints the `PASS AC-3: ` measurement line and the `FAIL AC-3: ` behaviour line together - which
is fine, but the reverse case (red measured, green behaviour) is impossible to route at all, because
the prefix lives on a line the (a) branch owns. So the measurement line keeps its own PASS/FAIL
verdict pair *and* the behaviour keeps its own: four printed branches, two conditions, each
line carrying exactly one token.

The shape, as a skeleton (target of the implementation; `ok` stays a derived name so B-05's shipped
PASS string survives unchanged):

```bash
measured_line = 'good=' + str(good.status_code) + ' bad=' + str(bad.status_code) + ' ' + str(bad.json())[:120]
if measured_ok:
    print('PASS AC-3: measurement line printed byte-for-byte (measured verdict fail-ac-three-measured)')
else:
    print('FAIL AC-3: ' + measured_line + ' (measured verdict fail-ac-three-measured)')
behaviour_verdict = 'PASS AC-3: NULL staff_pin_hash falls back to STAFF_PIN, wrong PIN still 401 AUTH_INVALID_PIN' if ok else 'FAIL AC-3: STAFF_PIN fallback not as specified ' + str(bad.json())[:120] + ' (behaviour verdict fail-ac-three-behaviour)'
print(behaviour_verdict)
import sys as _s; _s.exit(0)
```

`measured_ok = good.status_code == 200 and bad.status_code == 401` and
`ok = measured_ok and bad.json().get('error', {}).get('code') == 'AUTH_INVALID_PIN'`. The crash
guard becomes `|| { echo "FAIL AC-3: probe crashed (behaviour verdict fail-ac-three-behaviour)"; exit 0; }`
so the crash path routes through (b) and still exits 0 with a token.

### Why D-07's deliverable is a *pair* of edits (the finding that changes D-06's ruling)

D-06's ruling says AC-3 "is declared structurally red until B-05's AC-3 is re-specced". Measured
today on throwaway trees built from shipped `main` (`6424460`), with a `backend/.venv` symlink so the
probe actually runs: **the B-05 half alone does not make that arm green, and the D-06 half alone
cannot make it green either.** Three independent measurements:

1. Shipped D-06 AC-3's block, run against a B-05 AC-3 that already carries the split above: still
   red, `FAIL AC-3: B-05 AC-3 bare-line[good=200 bad=401 {'error': {'code': 'AUTH_INVALID_PIN',
   'message': 'AUTH INVALID PIN'}}|]`. Its `BARE=` filter uses the unanchored pattern
   `^FAIL AC-3|^PASS AC-3`, which does not match the `PASS AC-3: ` token followed by a colon, so the
   probe's own green measurement line is counted as a bare line forever.
2. Same green split tree, against D-06 AC-3 with only the obvious `BARE=` token-boundary repair:
   still red, `FAIL AC-3: B-05 AC-3 bare-line[...]`, for a second shipped bug in the same block:
   `${MISS% }` strips the first space in `${MISS}` rather than the intended trailing one, so a
   `bare-line[...]` arm - whose payload ends in `]]` - re-emits every later arm inside itself and the
   block's verdict line is unparseable garbage while the AC it reports on is green. Both fixes are
   inside D-06's scope (its round-b note already repaired this block once); D-07's AC-5 says so.
3. D-06 AC-3 with both repairs plus an armed shape gate, run against the shipped pre-split B-05
   AC-3: red, and *correctly* so - the gate cannot certify a shape it does not grade, so
   **D-07's implementation must add the gate itself** (AC-4 below).

Measurement 3 is also what makes the gate non-vacuous, together with its negative control:

- Armed gate against a B-05 AC-3 whose measurement line carries a `PASS AC-3: ` prefix while the
  single shared `ok` flag still decides both routings (i.e. an implementation that adds no
  independent (a) branch): runacs reports B-05 AC-3 `PASS`, and the gate reports
  `FAIL AC-3: B-05 AC-3 ac3-shape`. That `PASS` for a block that never decided (a) is exactly the
  false-green class D-04 exists to catch; only the gate sees it.

So the honest scope statement for D-07 is: land the B-05 split, land the D-06 AC-3 probe repair
plus gate, and prove the *combination* - not either half - is what moves each verdict.
