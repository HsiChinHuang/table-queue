## Goal

Give the staff surface its waitlist: one list endpoint that filters, searches, pages and sorts the
day's entries with the lazy no-show applied before the answer is produced, and nine action endpoints
(call, seat, no-show, restore, revert, cancel, edit, reorder) that move an entry along the section 5
state machine and keep the table row and the entry row in step.

## Context

B-06 (public join / status / cancel / board, plus `app/services/waitlist.py`) are merged on `main`.

Three contract readings are recorded before implementation starts, because each one is something an
AC pins and the documents do not settle in one place:

- **R-B07-1 (the reorder mismatch code is 409, not 422).** `POST /api/v1/staff/waitlist/reorder`
  declares exactly two non-success responses in `_docs/openapi.yaml`: `401` (`Unauthorized`) and
  `422` (`ValidationError`). It does **not** declare `409`, unlike the seven action operations that
  carry `WaitlistInvalidStatus`. `app/schemas.ReorderWaitlistRequest` validates only that
  `ordered_ids` is a list of UUID strings, so a list of well-formed UUIDs that is not exactly the
  current `WAITING` + `CALLED` set is not a schema failure - it is the staff user asking for an
  order over a queue that has changed under them, which is section 11's `CONFLICT` (409) or
  `WAITLIST_INVALID_STATUS` (409). The contract's 402-free answer wins: a set mismatch is 409 and
  the code must be one of the 409s section 11 defines, `CONFLICT` or `WAITLIST_INVALID_STATUS`.
  422 stays reserved for what the schema itself rejects (a non-UUID member, a missing key), and AC-14
  measures both halves of that line.
- **R-B07-2 (`search` has no SQL pattern anywhere in the contract).** `WaitlistFilterStatus` and the
  `search` parameter are described in one line: "Name or phone last 3 digits". The only real
  implementation of the second half already exists and is merged: `app.services.waitlist` spells a
  phone tail as `phone_last3(phone)` == the last three normalized digits, with separators dropped by
  `normalize_phone`. AC-4 therefore asks for exactly two hits out of four rows - a case-insensitive
  name substring and an exact match on the last three normalized digits - and asks nothing else of
  the search, because nothing else is specified. A candidate that reads the tail from the raw string
  instead of the normalized digits fails AC-4's hyphenated row.
- **R-B07-3 (`restore` returns the row to `WAITING` with a cleared hold, and the AC says which
  columns it reads).** `specs.md` 4.5 and the owner stub agree that `restore` clears `called_at`,
  `closed_at` and `hold_minutes_snapshot` and returns the entry to its original `sort_order`. The
  openapi `restore` example contradicts the prose: it shows `called_at` and `hold_minutes_snapshot`
  still populated on a `WAITING` answer. Prose wins (playbook section 1: openapi fixes field names
  and codes, specs fixes behaviour), and AC-12 asserts the prose's three clears. `original
  sort_order` is not a column - `WaitlistEntry` (B-02, merged, out of scope) has no such field - so
  the only thing an outside probe can observe is the outcome 4.5/4.6 name: after the queue has been
  compacted by a `reorder`, a `restore` lands the entry back in front of the rows that joined after
  it. AC-12 measures that outcome rather than a column.

## Measured on main, before implementation (the two probes that decide AC wording)

Both run on this worktree at `8d40c32`, which is `origin/main`. Verbatim output is in the
`Measured today:` line of the AC named beside each.

1. **Does the lazy no-show persist, or is it computed only?** `specs.md` 4.10 says "backend *sets*
   status to `NO_SHOW`, sets `closed_at`", and merged B-06 does exactly that:
   `app/services/waitlist.py::apply_lazy_no_show` assigns `NO_SHOW` + `closed_at` and calls
   `db.commit()`. Measured directly against the merged service on a seeded row (a `CALLED` entry with
   `called_at` 13:00Z and `hold_minutes_snapshot` 10, read at 13:20Z): the returned row reads
   `NO_SHOW` with `closed_at` stamped, and a fresh session sees the same `NO_SHOW` - so the
   transition is persisted, not computed per read. AC-3 pins the observable pair (the list answer
   *and* a second list answer both say `NO_SHOW`), which is the persisted reading and the only one
   the merged code can satisfy.
2. **What does `phone_masked` actually print?** `app/schemas.mask_phone` is a shape-preserving
   mask, not the one template the openapi example shows. Measured on the merged tree:
   `0900-000-001` gives `0900-***-001`, `0912345678` gives `*******678`, `02-123-4567` gives
   `02-***-4567`. So the invariant is "the last three digits survive and everything left of them is
   replaced by asterisks, one per hidden character", not "the string starts with `0900-`". AC-4
   asserts the invariant on a row whose phone is typed in the contract's own form, so the printed
   value is exactly the contract example `0900-***-001` while the check stays true for the other
   shapes the merged mask produces.
