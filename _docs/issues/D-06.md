### A - a scope check that is false-red on `main` today (reproduced, not asserted)

`_docs/issues/D-04.md` AC-4 attributes paths to HEAD with `git show --name-only --format= HEAD` and
prints `FAIL AC-4: no paths attributable to HEAD to scope-check` when that yields nothing. Measured on
three history shapes:

| shape | sha | `git show --name-only --format=` | `-m --first-parent` |
|---|---|---|---|
| normal commit | `4d91751` | `_docs/testing.md` | `_docs/testing.md` (identical) |
| merge commit | `afa511d` | *(empty)* | `_docs/issues/F-16.md _docs/issues/P0-08.md _docs/testing.md` |
| parentless root | `8e32ca7` | all 29 root paths | all 29 root paths (identical) |

So D-04 AC-4 is green on a branch tip and permanently red on merged `main`. The same class sits in
`_docs/issues/D-05.md` AC-8's `TICKED=` line (`git diff HEAD~1..HEAD`), and there the failure mode is
worse than red: measured at a real merge commit,
`git diff HEAD~1..HEAD -- '_docs/issues/*.md' | grep -cE '^+- \[x\] \*\*AC-'` prints `0`, and the AC
reads that as "no checkbox churn" - **silently vacuous**, the exact class D-04 exists to eliminate.

A merge commit is not hypothetical here: `afa511d`, `36eb081` and `66887e4` are three of the last four
commits on `main`, and the two `HEAD~1..HEAD` lines in `_docs/issues/D-05.md` are shipped content that
meets its claim only when the verification tree happens to be non-merge.

The reproduction was run, not trusted. In a scratch copy of this branch (`git archive HEAD | tar -x`,
`git init`, one base commit, a one-commit branch merged back with `--no-ff`, merge `a820099`), the
D-04 AC-4 block, run verbatim against that synthesized merge commit, printed:

    FAIL AC-4: no paths attributable to HEAD to scope-check

AC-4 of *this* issue therefore does not check whether `_docs/issues/D-04.md` mentions a flag - a grep
for `--first-parent` there passes on a comment, which is keyword soup. It extracts the real block and
runs it against a merge commit, a normal commit and a parentless root that it synthesizes itself in a
scratch directory from the repo's own history, and requires each run to produce a verdict token. It
also requires the *pre-repair* block to still be false-red on that same merge commit, so the test
cannot quietly stop testing the shape it was written for. That is what "falsify it under the
merge-commit shape specifically" costs, and it is the only form that can still fail after the previous
rewrite: AC-4 was already rewritten once (D-04 round-1 F-2) to escape `git diff HEAD~1..HEAD`, and the
replacement reintroduced the same blindness class.

### B - failure paths graded `silent` instead of red (ruling included)

`_docs/issues/B-05.md` AC-1 and AC-3 report their bad path with a bare measurement
(`print(' '.join(bad) ...)`, `print('good=' + ...)`) and no `FAIL AC-n:` token, so runacs cannot see
the failure. Re-measured by reconstruction at `0d10554`: the last commit touching `_docs/issues/B-05.md`
is `36eb081` (its merge), whose first parent is `66887e4`, at which
`git show HEAD~1:_docs/issues/B-05.md` is still the pre-implementation draft - whose AC-1 block begins
`test -f backend/app/routers/auth.py || { echo "FAIL AC-1: ..."; exit 0; }`. At the merge commit itself
`git show HEAD~1:...` follows the first parent into *draft* content again, so a run there is a false
red, not a green: **B-05's ACs are gradable on the branch tip only, and the closed issue carries no
note saying so.** That is defect A's shape-dependence arriving at a different AC, and it is why AC-2
and AC-3 of this issue compare extracted blocks rather than trusting a run at one tree.

**Ruling (asked, answered, recorded).** B-05 and D-04 are closed and merged. Editing a closed issue's
AC text is legitimate in exactly one class, and this issue stays inside it: **token-only,
assertion-preserving repairs** - add the missing verdict token on the failure path, add a provenance
note, delete a dead line - where the set of trees the AC accepts or rejects is provably unchanged.
AC-2 and AC-3 are written so that they *derive* that invariant instead of asserting it: each extracts
the pre-repair block from the last pre-repair blob and requires the repaired block to agree with it
(token set in AC-2, byte-identical non-failing output in AC-3). What is **not** legitimate, and is out
of scope here, is changing what a closed AC claims - its thresholds, its probe, its target. If a closed
AC's claim turns out to be wrong, the fix is a new guard AC in a new issue, not a rewrite.

### C - an AC that cannot pin the number in its heading (honesty, not strictness)

`_docs/issues/B-05.md` AC-6 is headed "rate limited to 5 requests per minute". Re-measured: the literal
`5/minute` occurs twice in the file, both in prose outside any fenced block, so no AC block can
distinguish `5/minute` from `5/hour` - the input measured both as `401,401,401,401,401,429`, and 30
rapid attempts as 30x`429` either way. A fixed-window counter cannot separate the two from inside one
window, so the remedy is **not** a stricter probe; a stricter AC would be a lie of a different shape.
The remedy is that the AC states the limit where the check lives, and states what the probe cannot
decide, so no reader mistakes green for "the window length was verified".

This is defect B's honesty gap in the opposite direction: B was a failure the tooling could not see, C
is a success the tooling over-reports. AC-5 pins it without going keyword-soup, in two ways. It requires
the literal `5/minute` to sit inside AC-6's **fenced block** - in its `PASS AC-6:` / `FAIL AC-6:` verdict
strings, where a heading cannot satisfy it - and it requires the limitation to be carried by lines that
survive stripping comments, so it cannot be smuggled in as a `#` line. It then goes red again if anyone
adds a window-length *assertion* to AC-6, which is the guard against the tempting wrong fix.
`5/minute` in those verdict strings overstates nothing: AC-6's probe is exactly 6 login requests and its
verdict already reads "first 5 attempts pass the limiter, 6th is 429", so the limit is stated where it is
checked, not newly asserted elsewhere.

The same judgement applies to `_docs/issues/B-06.md` AC-14 (`10/minute`). B-06 is open and its SW is
working right now, so its AC blocks are off limits; AC-6 here guards only that the caveat already in its
Implementation notes is still there, and that this issue itself declares B-06 out of scope.

## Behaviour

A reader who runs an AC gate on merged `main`, on a branch tip, or on a first commit gets a verdict token
in all three cases, and the ones that cannot decide say so instead of reporting success. A failure inside
a closed issue's AC is visible to the tooling that grades it. The guide's counts match the tool's output,
and the guide names the places where its own endorsed shape can hide information.

## Implementation notes

- The repairs to closed issues are ruling B's token-only class: no threshold, probe body, request count
  or target path changes, and AC-2/AC-3 *derive* that from the pre-repair blob rather than asserting it,
  so a later edit that weakens an assertion turns the AC red instead of being blessed by it.
- Pre-repair blobs are read with `git show HEAD:<path>`, never from a path-derived cut-off commit.
`_docs/issues/B-05.md` has exactly one touching commit, `d897a1b`, and it is not an ancestor of this
branch's `HEAD`; an earlier draft of AC-2 captured `git rev-list -n1 -- _docs/issues/B-05.md` inside
`$(...)`, and because git exits **0 with empty stdout** when a path has no commits at or below the
rev, the capture succeeded, `T` became empty, and the AC died on an unrecoverable baseline it could
never fix. That is a fifth instance of this issue's defect class - a check that reads as a repo
problem but is a property of the check - and it was found by running the AC, not by reading it. An AC
whose baseline depends on commit reachability must say so, or read from a ref that always resolves.
A repair that has not landed yet means the repaired AC is red today, and its `Measured today:` line
says so rather than hiding behind a fake baseline.
- AC-4 synthesizes all three git shapes it needs (`--no-ff` merge, one-parent, parentless root) with
`git init -b main`, `git commit --orphan` and `git merge --allow-unrelated-histories` **inside** its
`mktemp -d` tree, and counts parents with `git log -1 --format=%p | wc -w`. Three traps, each hit by
running the draft rather than reading it: the archive-extracted scratch repo has only its own commits,
so `git checkout <real-repo-sha>` dies with `reference is not a tree` and no shape can be sampled that
way; an orphan commit has **zero** parents, not one, so the one-parent shape has to be an ordinary
second commit on `main`; and `git rev-list --no-walk --count --parents` is not a parent counter - it
emits `count commit parent...`, so the count is always 1 and every shape test built on it silently
tests the wrong shape. Because all three shapes are synthesized rather than borrowed from history,
AC-4 is executable in an archive copy and at the QA detached checkout, where the real merged `main`
history is not reachable at all.
- AC-4, AC-8 and AC-10 write only under `mktemp -d` and delete it on exit; AC-4 additionally runs
  `git init`/`git archive`/plumbing **inside** that directory and never inside the repo, so the
  verification tree and the QA detached checkout are never mutated, and nothing checks out a commit in
  the tree the gate is grading. AC-4 needs `git init -b` (git 2.28+); if `init` refuses the flag the block
  fails loudly on its own init check rather than passing quietly.
- The `TICKED` repair in `_docs/issues/D-05.md` must fail closed. `grep -c` prints `0` **and** exits 1 on
  no match, so its output must not be piped inside a command substitution, and the block must distinguish
  "no attributable paths" from "no checkbox churn" - defect A in one line of bash.
- Keep `_docs/testing.md`'s section numbering and every existing heading text: other issues cite sections
  by number and `_docs/issues/D-04.md` cites Rule 1 and the anti-patterns by name.
- AC-1..AC-10 read only paths under `_docs/` plus `git` plumbing, all present in the QA detached
  checkout, so every AC is runnable at the gate. Nothing reaches `.tq-orchestrator/`, `../`, or an
  absolute path. AC-6 is the only AC that reads `_docs/issues/B-06.md`, and only to assert here that it
  must not be edited; the Out-of-scope sentence naming that file is what makes AC-6's green side
  reachable, so keep the path literal in an Implementation notes line as well as in Out of scope.
- EOL is LF; English only, no CJK (AC-10 is this issue's own CJK guard).
