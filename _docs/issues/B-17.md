## Goal

Two things are true when this is done: a whole-backend `pytest -q` run passes with zero failures
under the default (random) ordering, because no test module leaves a rebound engine, session
factory or `DATABASE_URL` behind; and every AC in the repo that claims a suite-wide pytest verdict
names its ordering pin explicitly, so a closed issue's verdict does not depend on which plugins the
machine happens to have installed.

block red although every property it guarded was green: that runner collects verdict strings line-wise
out of the merged output and files a block red if any collected string starts with the failure word, so
a verdict that shares a stream with a diagnostic cannot be trusted - and the diagnostic did not even
have to be a real verdict line, only to look like one. That is why the probe writes reasons to a scratch
file and stdout carries only the verdict, and why this AC treats a leaked verdict string as its own
failure rather than as cosmetics. The instrument is honest about its limit: the guard catches a leaked
line beginning with a verdict string, and a reason placed after the verdict line would still be caught
by the runner's merge but not by this guard's ordering check, so the block simply never writes reasons
to stdout at all.
