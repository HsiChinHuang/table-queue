## Goal

Serve the one dashboard the contract declares - `GET /api/v1/staff/dashboard` - so a staff client
gets the live queue counts, the live table counts and the day's rollups from a single authenticated
call, with the lazy no-show applied before any of those numbers are computed.

## Context

B-02 (models), B-03 (schemas, including `DashboardResponse`), B-04 (the `Staff` / `DbSession` /
`get_now` seams and the error envelope), B-05 (staff JWT), B-06 (`app/services/waitlist.py`) and
B-08 (`backend/app/routers/staff.py`, mounted through `app/main.py`'s `mount()` helper) are merged
on `main`. This issue adds one read-only operation onto that surface.

Measured posture of `main` at `ee8bfbb`, which the ACs were written against rather than assumed:

- `app.openapi()["paths"]` lists 14 paths and **none** of them is `/api/v1/staff/dashboard`, so every
  behavioural AC below starts red and its guard prints rather than staying silent.
- `app.schemas.DashboardResponse` (B-03) already exists and declares all ten fields, but with
  `no_show_today` / `cancelled_today` / `seated_today` / `avg_wait_minutes_today` as
  `int | None = None`, i.e. **optional** in Python while openapi marks only the six live counters as
  `required`. `extra="forbid"` is already set, so a stray key in the payload is a response-model
  error rather than a silent extra field.
- `app.services.waitlist.business_date_for(branch, now)` is the merged business-date rule
  (`(now_in_branch_tz - cutoff_hour).date()`) and `apply_lazy_no_show(db, entry, now)` is the merged
  section 4.10 transition, and it **commits** rather than computing. AC-7 reuses the second and AC-6
  the first, so the dashboard cannot invent its own midnight or its own expiry test.
- `app.services.tables.list_tables(db, include_inactive)` is the merged "active tables only" read
  that B-08's AC set already exercises; AC-5 counts through it (or through the same `is_active`
  predicate) rather than inventing a third table query.

Four contract readings are recorded before implementation starts, because each is something an AC
pins and the three documents do not settle it in one place:

- **R-B09-1 (`no_show_today` / `cancelled_today` / `seated_today` are required in the wire shape;
  `avg_wait_minutes_today` is the only field that may be null).** The owner stub asserts all four
  "return", and `_docs/openapi.yaml:1737` resolves it: `DashboardResponse.required` names exactly the
  six live counters, and of the four remaining fields only `avg_wait_minutes_today` carries
  `nullable: true`, with the operation's own example showing all ten keys. So the three day counters
  are integers on the wire (0 when nothing happened today) and only the average may answer null.
  `app.schemas.DashboardResponse` making the three optional is looser than the contract and cannot
  be tightened here (B-03's file, out of scope), so AC-3 pins the **contract** shape on the response
  and says in its prose that a `null` for one of the three is a FAIL even though the shipped model
  would accept it.
- **R-B09-2 (`avg_wait_minutes_today` is not defined anywhere, so the AC pins the only reading the
  contract's example can satisfy, and AC-9 pins the null half instead).** `_docs/specs.md` never
  names this field, never names a wait-duration formula, and the only duration the file defines is
  seat-to-close (`created_at`/`seated_at` to `closed_at`); `avg_seat_minutes` is a *forward*
  estimation rate (section 7, used by `estimated_wait_minutes`), not a historical rollup, and
  section 8's `avg_wait_minutes` example of 25 for a *live* guest is a different field with a
  different name. With no prose to read, the operation example at `_docs/openapi.yaml:878` is the
  only evidence: `waiting_count: 5, called_count: 1, seated_count: 2, no_show_today: 1,
  cancelled_today: 2, seated_today: 8, avg_wait_minutes_today: 18`. A "today" average that counted
  the live `WAITING` / `CALLED` / `SEATED` parties would need a `closed_at` those rows do not have,
  and would have to average 14 rows to reach 8 - the only population the other nine fields describe
  is the finished ones. So AC-9 pins two things that every plausible implementation must satisfy and
  nothing else: the field is null exactly when no row closed today, and where it is an integer it is
  an integer of that same same-day finished population, never a float and never a value drawn from a
  row outside the day. AC-8 fixes the one worked case this groom could defend - two rows closed
  today at 20 and 40 minutes, average 30 - and states in prose that the mean is `int()`-ed, matching
  the merged `_elapsed_minutes` floor-truncation and the contract's `type: integer`; the floor
  boundary (20 and 41 gives 30, not 30.5) is the whole of its discriminating power.
- **R-B09-3 (the lazy no-show is a dashboard obligation, and only its *persistence* is observable
  from this endpoint).** `_docs/specs.md:214` names `GET /staff/dashboard` as one of the three reads
  that apply section 4.10. A dashboard response carries no entry objects, so the AC cannot assert the
  flip *through* the dashboard. What it can assert, and what AC-7 does assert, is the half that is
  contract-visible and that a stubbed-out call cannot fake: a `CALLED` row past its hold is
  `NO_SHOW` in the database after the dashboard call, and the dashboard's own `waiting_count` /
  `called_count` / `no_show_today` already reflect it on that same response. AC-7's negative control
  is the mutation that proves the assertion is the load-bearing one (the expired row counted as
  `called_count` while the row stays `CALLED`) and it is measured to move.
- **R-B09-4 (`seated_today` counts today's `SEATED` rows, matching `seated_count`; the openapi
  example's 2-vs-8 is an unresolvable contradiction and is claimed by nobody).** The stub says
  "`seated_today` (current `business_date`)", and the day rollups beside it are all filtered by
  `closed_at`-within-the-day semantics, but the merged model offers no `seated_on` column:
  `WaitlistEntry` timestamps are `created_at` / `updated_at` / `called_at` / `seated_at` /
  `closed_at`, and `created_at` is the queue-join instant, not the seating instant. Meanwhile the
  operation example shows `seated_count: 2` and `seated_today: 8` in one payload, which is only
  coherent under a population this issue cannot derive from any documented rule (a
  `seated_at`-within-the-day reading is contradicted by the same example's own arithmetic, since 8
  seated parties cannot leave 2 seated out of the 14 rows that example describes). This is a real
  contract gap, not a puzzle to solve in a groom: AC-4 therefore pins the reading the stub states
  (rows whose `business_date` is today and whose status is `SEATED`, which makes `seated_today` equal
  `seated_count` on every seed this file uses) and AC-4's prose says so plainly, while the alternative
  reading is filed as a docs repair below rather than being smuggled in as a second AC. An
  implementation that later reads the field as "seatings that happened today" is compatible with AC-4
  only on seeds where the two populations coincide, which is exactly what AC-4's `yesterday` rows are
  for: they carry `seated_at` at the frozen instant but a prior `business_date`, so a counter that
  ignores the day filter is visible and a counter that keys on `seated_at` instead of
  `business_date` is visible too.

- Take the response shape from `app.schemas.DashboardResponse` and define nothing new. Return a plain
  dict from the handler and let `response_model` validate it (`extra="forbid"` is already set, so a
  stray key is loud).
- Reuse rather than re-derive: `get_now()` for the clock,
  `app.services.waitlist.business_date_for(branch, now)` for the day,
  `app.services.waitlist.apply_lazy_no_show(db, entry, now)` for section 4.10, and
  `app.services.tables.list_tables(db, include_inactive=False)` or the same `is_active` predicate for
  the table half.
- Order matters once: read what is needed, then apply the lazy no-show, then count. The merged
  `apply_lazy_no_show` **commits**, which ends the transaction the read opened - the module docstring
  in `app/services/waitlist.py` says so, and AC-7's post-call status read is what notices if the
  order is reversed.
- Naive-vs-aware is the trap this stack enforces: `DateTime(timezone=True)` stores naive on SQLite
  (R-B08-4), so re-attach UTC before subtracting `seated_at` from `closed_at`; an aware-minus-naive
  `TypeError` becomes 500 `INTERNAL_ERROR`, which every behavioural AC here would read as a status
  failure rather than as an arithmetic one.
- Do not add a second response field, a query parameter, or a second endpoint: the contract declares
  exactly this one operation with no parameters.
