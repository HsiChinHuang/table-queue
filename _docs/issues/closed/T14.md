## Goal

Make the staff waitlist board render at scale: the Closed section is capped (last 50 rows + a
working show-more), the Active list render is bounded (virtualised window or pagination — no
unbounded `.map` over all entries), the 3s full-list `refetchInterval` is replaced by
invalidate-on-mutation, and a committed perf-style test pins the N=200 render budget and proves
the jsdom scale case C-PROOF-3 completes and reports measured numbers instead of stalling.

## Reason (audit provenance)

SEC AUDIT LOW-MEDIUM (C-8): unbounded .map renders x 3s refetch x per-card timers on an all-day shared tablet; audit harness itself stalled at 240s rendering this page - consistent signal, numbers pending. Severity low-medium.

## Context

C-8 mechanism on the waitlist board (HEAD `53bc7c6`):

1. **Unbounded `.map` renders** — `sortedActive.map` (WaitlistPage.tsx ~line 604) renders every
   active entry as a full `WaitlistCard` (3+ lucide SVG icons, up to 4 action buttons each), and
   `sortedClosed.map` (~line 657) renders every closed entry. An all-day shared board accumulates
   hundreds of entries, so render cost grows without bound.
2. **3s full-list refetch** — `refetchInterval: 3000` on BOTH the dashboard query (line 169) and
   the waitlist-list query (line 182): a full fetch plus a full re-render every 3 seconds,
   regardless of activity. `staleTime: 5000` does not help (3000 < 5000 means every interval tick
   is a real refetch).
3. **Per-card timers** — `Countdown` intervals mount per CALLED entry with a `targetTime`
   (WaitlistCard.tsx); timer count scales with the number of called cards on screen.

**Root cause of the jsdom 240s audit-harness stall — MEASURED at HEAD `53bc7c6` (WSL, node22
vitest), not a test artifact:**

- `const waitlistData = waitlistRaw ?? []` (WaitlistPage.tsx line 178) creates a **new array
  identity on every render** while the query is loading.
- The "Last updated" effect (lines 361-366) depends on `[waitlistData, dashboard]` and runs
  `if (waitlistData || dashboard) setLastUpdated(new Date())`. While loading, `[]` is truthy, the
  dep changes on every render, and the effect therefore calls `setLastUpdated(new Date())` on
  every render → state change → re-render → effect re-runs → **infinite synchronous re-render
  loop in the loading state**.
- Proof chain (all executed at HEAD): a minimal replica of the page WITHOUT this state+effect
  renders fine; adding the exact 6-line state+effect turns the identical replica into the infinite
  loop (K6 probe). A traced copy loops at 100K+ cycles/sec (7.1M-line trace). A 1s-interval
  watchdog ticks 0 times during the loop — the event loop is fully blocked, which is exactly the
  "stall" the audit harness observed. The full page with ALL component and lucide imports stubbed
  still loops (not a component-graph issue). Bisecting away all 8 mutations, the 300ms search
  debounce, all memos, the loading skeleton, and even the QueryClient wrapper still loops. A probe
  with a RESOLVING N=50 API also still loops: the loading-phase loop starves promise microtasks,
  so in act-based jsdom tests the data never arrives — **the page cannot be mounted in jsdom at
  all until this loop is fixed**.
- Consequence for the fix: the SW fix must ALSO break this loop (e.g. stabilise `waitlistData`
  identity with `useMemo`, and/or gate `setLastUpdated` on real data arrival). AC-5 arm 1 is the
  mechanical guard for this; AC-1/AC-2/AC-5 arm 2 can only go GREEN once the loop AND the list
  bounds are both fixed.

Environment: frontend tests run under WSL with the node22 binary (WSL Node 18 ESM is broken);
`frontend/node_modules` is already linked — do not `npm ci`. The exact command is in each AC
block below.

Related: T31 (#86, server-side SQL pagination, backlog) is NOT a dependency — AC-2 is
satisfiable without it via client-side windowing/pagination. `package.json` is frozen (F-12), so
virtualisation must be dependency-free.
