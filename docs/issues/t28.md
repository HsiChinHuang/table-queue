1. **ac1 — contract doc pins the exact algorithm.** `docs/tooling/ready-contract.md`
   exists and states: closed-set = the set of ids in `_docs/issue-map.json`
   whose mapped platform issue number has platform state `closed` (number→id
   via the issue-map); readiness is NEVER computed from issue titles (no title
   regex anywhere in the readiness path); a dep-map gap produces a per-issue
   `UNKNOWN-deps` report while all other issues keep evaluating (no whole-run
   abort).
2. **ac2 — regression scenario + location note in the doc.** The doc contains
   the 4 observed reopens as the regression scenario — B-15 `#47`, F-16 `#48`,
   P0-16 `#49`, P0-13 `#46` (all platform-closed, all listed ready by the old
   title regex) — plus the out-of-repo location note `../.tq-orchestrator/ready.py`
   and an explicit note that the tool is absent on this host and the fix is
   deferred.
3. **ac3 — closed bare-title fixture case.** Self-contained fixture
   `tests/ready_contract/ready_fixture.py` (Python 3 stdlib only, offline, no
   network/platform API) embeds a mini reference implementation of the
   contract. `--case closed-bare-title` passes: a closed issue with a bare
   (unbracketed) title counts closed; negative control — two issues with
   identical map/state data but different titles classify identically, so a
   title change can never flip an issue back to READY.
4. **ac4 — dep-gap fixture case.** `--case dep-gap` passes: the issue with a
   dependency missing from the dep-map is reported `UNKNOWN-deps` for THAT
   issue only; in the same run at least one other issue evaluates READY and
   one WAITING (no whole-run abort); exit code 0.
5. **ac5 — full offline run.** `--case all` passes from the repo root with no
   network or platform API access (both cases green in one run).
