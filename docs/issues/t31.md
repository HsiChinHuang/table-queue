## Reason (audit provenance)

SEC AUDIT MEDIUM (B-2): limit unbounded+negative-tolerant and sliced in PYTHON after full fetch - every list call is O(rows) on a non-rate-limited staff surface; limit=-1 answers 200 empty-items-nonzero-total (silently wrong pagination). Severity medium.

## Context

The security audit (phase-5) flagged `GET /api/v1/staff/waitlist` as a non-rate-limited
staff surface (section 15 budgets login, join and lookup only) whose list path materialises
the whole day before answering a page. Measured facts at grooming time (pre-fix):

- **The paging lives in Python, not SQL.** `list_waitlist`
  (`backend/app/services/staff_waitlist.py`) calls `queue_rows`, which ends in
  `query.order_by(*_queue_order()).all()` — every row of the day's filtered set is fetched —
  then computes `total = len(rows)` and slices
  `page = rows[max(offset, 0) : max(offset, 0) + max(limit, 0)]`. Every list call is
  O(day size) regardless of `limit`.
- **`limit=0` answers 200 with empty `items` and non-zero `total`.** Reproduced live
  (throwaway SQLite, seeded store): `GET /api/v1/staff/waitlist?limit=0` →
  `200 {'items': [], 'total': 7}`. `max(limit, 0)` turns a zero/negative limit into an empty
  page while `total` still reports the filter size — silently wrong pagination.
- **t29 (Platform #84, merged `9afadc6`) already moved the negative bound to the schema
  layer.** The route now binds `limit: int = Query(default=100, ge=0)` and
  `offset: int = Query(default=0, ge=0)`, so `limit=-1` answers 422 today (re-confirmed at
  grooming). **t29's `ge=0` on `limit` is refined here to `ge=1`**: a `limit=0` page is
  meaningless for a list endpoint, so it must be rejected rather than answered 200-empty.
  t29's spec stands as-is historically; t31 is the refinement. The **no-page-size-cap
  decision is kept** — `limit` gets no upper bound. t29's merged test
  (`backend/tests/test_t29_int_bounds.py`) asserts only that *negative* `limit`/`offset` are
  422, so it stays green under `ge=1`.
- **`queue_rows` is a function in `staff_waitlist.py`, not a module.** The survey stub's
  file list named `backend/app/services/queue_rows.py`, which does not exist; the AC below
  targets the `queue_rows` function and its callers in
  `backend/app/services/staff_waitlist.py` (and the route binding in
  `backend/app/routers/staff_waitlist.py`).
- **`queue_rows` has a second caller that must keep the full set.** `active_rows` feeds
  `reorder`, whose contract (R-B07-1) requires the *exact* active set — paging is therefore
  opt-in: the list path passes the bounds, the reorder path does not.
- **`search` is applied in Python, after the fetch.** `_matches_search` matches a name
  substring or the last three *normalized* phone digits, and no column stores the normalized
  tail, so a SQL `LIMIT` cannot sit before the search filter without changing search
  semantics. Scope ruling: the **no-search path is fully SQL** (COUNT + bounded SELECT);
  the search path must still page *correctly* (total = match count, page = the
  `limit`/`offset` slice of the matches) but is not required to be O(limit). See Out of
  scope.

See `docs/plan.md` (security-audit remediation milestone) and the audit batch.

## Acceptance criteria

- **AC-1 — `limit` is `ge=1`, `offset` is `ge=0`, no upper bound.** The route binds
  `limit: int = Query(default=100, ge=1)` and `offset: int = Query(default=0, ge=0)`;
  `limit` carries no `le`. `GET /api/v1/staff/waitlist?limit=0` returns 422 whose body
  names the `limit` field; `limit=-1` and `offset=-5` each return 422 (t29's negative
  rejection preserved); `limit=1` returns 200 with exactly one item.
- **AC-2 — the page is the SQL slice of the ordered list (N=200 fixture).** With 200
  fixture rows added to the seeded day: the page at `limit=10&offset=0` has exactly the
  same item ids, in the same order, as the first 10 of the full ordered list; the page at
  `offset=total-3` has exactly the last 3 item ids; `offset=total` returns 200 with
  `items: []` and `total` unchanged; queue order (`sort_order`, then `created_at`) holds
  within every page.
- **AC-3 — `total` is the filter size, from COUNT, independent of paging.** `total`
  equals the number of rows the filter (status group, day, `party_size`) matches and is
  identical for `limit=1&offset=0`, `limit=50&offset=100` and `limit=1&offset=500`;
  `status=ALL` total is >= the default `ACTIVE` total; the `party_size=2` total is
  strictly between 0 and the unfiltered total on the fixture day.
- **AC-4 — the page SELECT is bounded in SQL; `total` comes from a COUNT statement.**
  On the no-search path, executing `limit=10&offset=20` issues a SELECT for the page
  carrying `LIMIT` and `OFFSET` with bound values 10 and 20, and a `COUNT` statement over
  the same filter — verified by capturing executed SQL on the engine
  (`sqlalchemy.event` `after_cursor_execute`), not by timing. The service no longer
  materialises the day's full row set to answer the page.
- **AC-5 — response shape unchanged; the full-set path stays intact.** The list body is
  exactly `{items, total}` with each item carrying the `WaitlistEntryResponse` fields
  (`id`, `queue_number`, `full_queue_number`, `status`, `party_size`, `created_at`,
  `updated_at`, `name`, `phone_masked`, `note`, `source`, `cancelled_reason`,
  `called_at`, `seated_at`, `remaining_seconds`, `hold_minutes_snapshot`, `table_id`,
  `table_label`); `POST /api/v1/staff/waitlist/reorder` still receives the *full* active
  set — a reorder naming every id of the full default list succeeds (200) and returns
  that exact order.
- **AC-6 — `search` and `party_size` compose with paging.** `search=Fix` (matching the
  200 fixture rows) returns `total == 200`; `limit=10` returns the first 10 matches in
  queue order (the prefix of the full filtered list); `offset=195` returns the last 5
  matches with `total` still 200 — i.e. offset applies to the filtered set, and `total`
  counts matches, not the page.

## Out of scope

- **Pushing the `search` predicate into SQL.** The three-digit phone-tail match is a
  comparison over normalized digits no column stores; SQL-pushing it would change search
  semantics (e.g. Unicode casefolding). The search path keeps its current matching and
  only gains correct paging/total (AC-6); making the search path O(limit) is a follow-up
  if profiling ever shows it matters.
- **A page-size cap on `limit`.** Product decision from t29: no upper bound.
- **Rate limiting the staff surface.** Section 15 budgets login, join and lookup only;
  the contract declares no 429 here.
- **The reorder full-set fetch.** `active_rows` must keep fetching the whole active set
  (R-B07-1); only the list path is paged.
- **t29's spec or tests.** t29 stands as merged; t31 refines the `limit` bound only.
