## Reason (audit provenance)

SEC AUDIT MEDIUM (C-4 C-7 C-9, C-3 redirect half): expires_at delivered-but-never-consumed (expired token keeps UI mounted + replays); AudioContext per beep never closed (accumulates to Chrome cap = audio dies mid-shift); untracked post-unmount timer. Severity medium.

## Goal

When this is done: the staff JWT's lifetime drives the client. The single staff store holds `expiresAt` alongside the token (set from the login response's `expires_in`, persisted, swept by `destroySession`); a rehydrated or timer-expired session is treated as logout — staff UI unmounts, storage is swept, and no request ever carries the known-expired bearer. The 401 handler redirects via `location.assign(ROUTES.STAFF_LOGIN)` with an already-on-login guard (no hardcoded path, no `location.href` assignment). Every countdown display in the app is driven by ONE shared 1Hz ticker (WaitlistCard fan-out and the guest status countdown keep ticking), SoundToggle reuses one lazily-created AudioContext that is closed on teardown with the first-interaction unlock registered once, and `useConnection.resetFailure`'s 3s timeout is tracked and cleared on unmount. The full frontend suite and `tsc --noEmit` are green; nothing outside `frontend/` changes.

## Acceptance criteria

All conditions are observable in the browser/devtools or in vitest (jsdom + fake timers). All blocks run from the repo root; test files live next to their sources under `frontend/src/`.

### AC-1 — the store keeps `expiresAt` with the token, and a rehydrated or timed-out expiry is treated as logout

- The single staff store (`frontend/src/stores/staffStore.ts`) holds `expiresAt` (epoch milliseconds, `number | null`) alongside `token`. Every token write made from a login response sets `expiresAt = Date.now() + expires_in * 1000` (±5 s clock tolerance in tests), so no code path can store a token without an expiry. The persisted `staff-storage` envelope carries `expiresAt` (it survives a reload via hydration), and `destroySession()`/logout null it together with the token.
- **Hydrated guard**: if the store rehydrates with a token whose `expiresAt` is in the past, the session is treated as already logged out before any staff UI renders: in-memory `token` is null, all four storage slots are empty (`destroySession` semantics), and `StaffLayout` renders the redirect to login rather than the staff area.
- **Expiry timer**: while a session is live, a watcher fires at `expiresAt` and performs the same sweep (`destroySession` — token null + slots empty) with no network call. Advancing a fake clock past a live session's expiry produces the sweep; a not-yet-expired session is untouched.
- Test: new cases in `frontend/src/stores/staffStore.test.ts` and/or `frontend/src/layouts/StaffLayout.test.tsx` (fake timers; stubbed login response with `expires_in`).

### AC-2 — `request()` refuses to send a known-expired bearer

- In `frontend/src/api/client.ts`, `request()` consults the stored `expiresAt` before attaching the `Authorization` header. If the stored token's `expiresAt` is at or before "now", that token MUST NOT go out: the call either short-circuits to a rejected `ApiError` (code `AUTH_TOKEN_EXPIRED`, status 401) before `fetch` is invoked, or the outgoing request carries no `Authorization` header. No outbound fetch may ever carry `Bearer <expired token>`.
- A live token (`expiresAt` in the future) is sent exactly as today (`Bearer <token>`), and a token with no known expiry is sent as today (unknown ≠ expired).
- Test: new cases in `frontend/src/api/client.test.ts` (stubbed fetch + `staffStore` seeded with an expired and a live token; assert on the recorded `fetch` init headers).

### AC-3 — the 401 redirect is router-driven: `ROUTES` constant + `location.assign` + already-on-login guard

- The 401 branch in `frontend/src/api/client.ts` redirects with `location.assign(ROUTES.STAFF_LOGIN)` — the constant from `frontend/src/routes.ts` — and the literal string `'/staff/login'` no longer appears in `client.ts`; the `window.location.href = ...` assignment is gone.
- The redirect is guarded: if the current location's pathname is already `ROUTES.STAFF_LOGIN`, no navigation happens (a 401 surfaced on the login page — e.g. a stale background refetch — must not re-assign). `destroySession()` still runs on every 401.
- Test: new/updated cases in `frontend/src/api/client.test.ts` (stubbed `location`: 401 from a staff path → `assign` called with `'/staff/login'`; 401 while already on `'/staff/login'` → `assign` not called).

### AC-4 — ONE shared 1Hz ticker drives every countdown; WaitlistCard fan-out preserved

- `frontend/src/hooks/useCountdown.ts` sources every consumer from exactly one app-wide interval: across the whole tree, `setInterval` is called at most once with a 1000 ms period to drive countdowns (e.g. a module-level ticker with a subscriber set; the hook itself creates zero, or the module creates one). With N ≥ 3 concurrent countdown consumers there is still at most one 1Hz countdown interval.
- Fan-out preserved: with N ≥ 3 CALLED `WaitlistCard`s rendered together (staff list) and a standalone `Countdown` (guest-status shape), each display decrements independently by 1 s per 1000 ms and fires its own `onComplete` exactly once at zero.
- Existing behaviour pins hold (or are re-pinned to the new mechanism with a note in the test file): initial value = ceil of remaining seconds, clamp at 0 (never negative), `onComplete` fires exactly once at zero, a second `start()` does not double the tick rate, and unmounting leaves no state updates. The `DEF-F06-1` pin in `useCountdown.test.ts` is preserved if the semantics still hold or re-pinned with an explicit comment.
- Out of scope: the polling intervals (board/status 5 s, staff waitlist 3 s) are untouched — the shared ticker covers countdown displays only.
- Test: updated cases in `frontend/src/hooks/useCountdown.test.ts`, `frontend/src/components/Countdown.test.tsx` and `frontend/src/components/WaitlistCard.test.tsx` (fake timers; a `setInterval` spy proving ≤ 1 countdown interval for N ≥ 3 consumers; per-display decrement; unmount-all leaves no interval and no post-unmount updates).

### AC-5 — SoundToggle: one lazily-created AudioContext, reused across beeps, closed on teardown; first-interaction unlock registered once

- `frontend/src/components/SoundToggle.tsx` creates at most ONE `AudioContext` for the life of the app (a lazily-created shared singleton — created on the first user interaction that triggers a beep, never at mount). Every subsequent beep reuses the same instance; there is no per-beep construction.
- The context is `.close()`d on component teardown (unmount), so a logged-out terminal leaves no live audio context behind.
- The first-interaction unlock listeners (`click`/`keydown`) are registered once and not re-registered on every effect run/toggle: after any number of sound on/off toggles, a single user interaction still arms the first beep.
- Beep shape unchanged: 880 Hz sine, 0.3 s, gain ramp per `_docs/ui.md` §13.
- Test: new cases in `frontend/src/components/SoundToggle.test.tsx` (jsdom has no `AudioContext`, so stub a recording class: render enabled → 0 instances created; first click interaction → exactly 1 instance + oscillator started; toggle off→on to trigger a second beep → still exactly 1 instance; unmount → `.close()` called on that instance).

### AC-6 — `useConnection.resetFailure`'s timeout is tracked and cleared

- The `setTimeout(() => setIsRecovered(false), 3000)` in `useConnection.resetFailure` (`frontend/src/components/ConnectionBanner.tsx`) is tracked (ref) and cleared: (a) on unmount — no hook-owned pending timers remain after the consumer unmounts (timer count returns to baseline under fake timers) and advancing the clock afterwards causes no state update or error; (b) on a repeated `resetFailure` call — at most one pending 3 s "recovered" timer exists at any time.
- The component's existing 3 s "Updated just now" timer (already tracked + cleared in its effect) keeps working.
- Test: new/updated cases in `frontend/src/components/ConnectionBanner.test.tsx` (fake timers: fail×3 → recover → exactly one pending 3000 ms timer; unmount → timer count back to baseline, advancing 10 s is inert; two rapid `resetFailure` calls → still ≤ 1 pending timer).

- Full suite: `cd frontend && npx vitest run` exits 0 with zero failed test files and zero failed tests (groom baseline: 30 files / 244 tests; the count may grow with the new tests, never shrink silently).
- `cd frontend && npx tsc --noEmit` exits 0.

- No file outside `frontend/` and this issue file is modified (backend, `_docs/` untouched).
