## Context

Test-infrastructure reliability issue discovered during T21 post-merge verification (main
bf3d643) on a WSL host. It is a cross-module interaction between
`backend/tests/test_log_hygiene.py` (added by T21) and the pre-existing
`backend/tests/test_db_atomicity.py` (D-02/T9 era), not a product regression: the T21 merged
tree is byte-identical to the branch that passed 6 random-order runs. This issue makes the
stability guarantee testable and removes the mechanism the stub identified, on the current
native-Windows host.

## Reason (provenance)

Full-suite runs on the original WSL host flaked at ~1/3 rate:
`sqlite3.OperationalError: disk I/O error` in the setup of `backend/tests/test_db_atomicity.py`.
The flake occurred ONLY when `backend/tests/test_log_hygiene.py` ran earlier in the same pytest
session. `test_db_atomicity.py` alone was 5/5 green; the two-module combo flaked ~1/2.

## Root cause

Confirmed by recon of the four candidate files (native-Windows host, this grooming):

- `test_log_hygiene.py::test_500_traceback_is_redacted` is the only test in the suite that
  **corrupts, unlinks and recreates a database file that the app's shared engine
  (`app.database.engine`) points at**: it seeds via `public_fixtures.fresh_session()` (which
  does `drop_all`/`create_all` on the shared engine), then
  `Path("test.db").write_text("t21 probe: not a sqlite database file")`, probes the 500 path,
  and in `finally` does `db_file.unlink(missing_ok=True)` followed by
  `database.Base.metadata.create_all(bind=database.engine)` - recreating the shared engine's
  file out from under it.
- The shared engine is built at import time from `DATABASE_URL` (`sqlite:///./test.db` in the
  baseline environment) with `NullPool`, and a `connect` event puts **every** connection into
  `PRAGMA journal_mode=wal` - so the shared file carries `test.db-wal` / `test.db-shm`
  sidecars. The test unlinks the main file while the engine (and any in-flight request
  connection) is still bound to that path.
- `test_db_atomicity.py` itself is already isolated: its `db` fixture builds
  `_db_test_support.Database("d02_atomicity")` - a dedicated `_d02_atomicity.db` file, its own
  `create_engine`, its own sessions, disposed and unlinked on teardown. It never touches the
  shared engine. The flake therefore lands in its setup on the WSL host as the downstream
  victim of the shared-engine file churn above.
- Mechanism (stub hypothesis, confirmed as the risk to remove): on WSL `/mnt/c` (drvfs),
  SQLite's byte-range locking plus an unlink of a file whose handles/sidecars are still in
  flight leaves a dangling-handle state that a subsequent SQLite setup in the same session can
  hit with `disk I/O error`. On native Windows (this host) the same sequence does not surface:
  the capped groom baseline (below) is 10/10 green on the pair and 1/1 green on the full
  suite. The mechanism is environment-sensitive; the guarantee this issue buys is (a) the
  stability measurement on this host and (b) removal of the shared-engine dangling-handle
  exposure so the drvfs mechanism no longer has a handle to dangle.

**Groom baseline on THIS host (native Windows, MSYS2 git-bash, main @ 905f0b3):** the two-module
pair (`test_log_hygiene.py` + `test_db_atomicity.py`, `-p no:randomly`) ran **10/10 green**
(`8 passed, 2 xfailed` each run, ~1.1 s); the full suite ran **1/1 green**
(`388 passed, 2 xfailed`, 85 s). The drvfs flake does not reproduce here; per the stub the AC is
the stability guarantee plus mechanism removal, not a repro.

## Design

Isolate the shared engine from the corruption test; keep `test_db_atomicity`'s existing
isolation as a pinned invariant. No production code (`backend/app`) changes.

1. **`test_log_hygiene.py::test_500_traceback_is_redacted` must stop operating on the shared
   engine's file.** The corruption target becomes a dedicated throwaway file with its own
   engine (the `_db_test_support.Database` pattern, or an equivalent local engine), with
   `get_db` overridden for the probe request so the app reads the scratch file it then
   corrupts. The test's `finally` unlinks the scratch file instead of the shared engine's
   `test.db`, and the `create_all(bind=database.engine)` "restore the shared file" step is
   dropped (there is nothing to restore). The test's assertions (500 + `INTERNAL_ERROR` +
   traceback-present + binding-segments-absent) are unchanged.
2. **Defense in depth on the hygiene module:** after the corruption test, the app's shared
   engine is disposed (`database.engine.dispose()` in that test's teardown/finally) so no
   connection state of the process can outlive the file churn, and no `test.db-wal` /
   `test.db-shm` sidecars of the shared file are left behind.
3. **`test_db_atomicity.py` invariant:** it keeps its dedicated `_d02_atomicity.db` file and
   its own engine via `Database("d02_atomicity")` - no shared engine, no shared pool. This is
   already true; AC-4 pins it so a future refactor cannot reintroduce the shared pool.
4. **No assertion weakening:** both modules keep their exact test ids (4 + 6, of which 2 are
   `xfail(run=False)`) and their assertion lines are not reduced (baselines: 22 `assert` lines
   in `test_log_hygiene.py`, 38 in `test_db_atomicity.py`; pair run summary `8 passed,
   2 xfailed`).

## Acceptance criteria

- AC-1 (stability, this host): running `pytest tests/test_log_hygiene.py tests/test_db_atomicity.py -q -p no:randomly` 10 consecutive times yields 10 green runs (exit 0 each, `8 passed, 2 xfailed`, no `disk I/O error` or setup error). The tracked `backend/test.db` is restored after the loop.
- AC-2 (suite): the full backend suite (`pytest -q -p no:randomly`) exits 0 with no failures or errors; `backend/test.db` restored afterwards.
- AC-3 (mechanism removal, hygiene side): `test_500_traceback_is_redacted` alone still passes, and running it leaves `backend/test.db` byte- AND mtime-identical (the test no longer touches the shared engine's file), leaves no `test.db-wal`/`test.db-shm` sidecars, and the test disposes the shared engine in its teardown. FAILS pre-fix (the test currently rewrites and unlinks `test.db`).
- AC-4 (mechanism removal, atomicity side, invariant - PASSES pre-fix by design): `test_db_atomicity.py` uses its dedicated `Database("d02_atomicity")` file+engine and imports nothing from `app.database` (no shared engine, no shared pool).
- AC-5 (no assertion weakening, invariant - PASSES pre-fix by design): the pair still collects exactly 10 tests and its run summary is `8 passed, 2 xfailed`, and the assertion-line counts satisfy `test_log_hygiene.py >= 22` and `test_db_atomicity.py >= 38` (the pre-fix baselines).
- AC-6 (scope honesty, documentation - PASSES by construction): this spec states the scope explicitly: the original flake is WSL/drvfs-environment-sensitive and does not reproduce on native Windows (baseline 10/10 + 1/1); the fix removes the shared-engine dangling-handle mechanism the stub identified, and the guarantee on this host is the 10/10 pair stability plus that mechanism removal.

## Out of scope

- Fixing or emulating the WSL drvfs environment itself; the flake is not reproducible on this
  host and no WSL runner is part of this repo's verification.
- Changes to `backend/app` production code (the engine's `NullPool`/WAL design is correct for
  production; only the test's file churn is the defect).
- Changing the other `test_log_hygiene.py` tests' use of `fresh_session()` on the shared engine
  (their drop/create on `test.db` is ordinary suite behavior, tracked-file restore is handled by
  the verification commands); the defect is specifically the corrupt+unlink+recreate sequence.
- The pre-existing fact that `backend/test.db` is a tracked file (separate hygiene concern).
