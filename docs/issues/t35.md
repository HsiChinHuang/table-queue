## Reason (provenance)

Discovered during T21 post-merge verification (main bf3d643). Full-suite runs flake at ~1/3 rate: `sqlite3.OperationalError: disk I/O error` in setup of `backend/tests/test_db_atomicity.py` (pre-existing, D-02/T9 era). The flake only occurs when `backend/tests/test_log_hygiene.py` (added by T21) runs earlier in the same pytest session. `test_db_atomicity.py` alone is 5/5 green; the two-module combo flakes ~1/2.

Root cause (orchestrator observation, to be confirmed by SW): `test_log_hygiene.py::test_500_traceback_is_redacted` corrupts + unlinks + recreates the shared `test.db` via the app's shared engine. On WSL `/mnt/c` (drvfs), the shared engine's connection pool can retain a dangling handle to the unlinked file; the subsequent `test_db_atomicity.py` setup (which creates its own `_d02_atomicity.db`) then hits a drvfs SQLite byte-range-lock / dangling-handle race and fails with `disk I/O error`. This is an environment-sensitive test-infrastructure interaction, NOT a product regression (the T21 merged tree is byte-identical to the branch that passed 6 random-order runs).

## Acceptance

The full backend suite is stable on WSL: running the complete suite (or at minimum `test_log_hygiene.py` + `test_db_atomicity.py` together) 10 consecutive times yields 10 green runs (no `disk I/O error` setup errors). The fix must not weaken either test's assertions.
