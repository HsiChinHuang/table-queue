## Goal

`POST /api/v1/admin/reset` exists, is reachable, requires a staff bearer, refuses any environment
other than `development` with 403, answers 422 `VALIDATION_ERROR` unless the body carries
`{"confirm": "RESET"}`, answers `204` with no body on success, and that success really drops and
re-creates the schema through the shipped B-13 seeder so the database ends up a fresh seed again.

## Context

The contract already declares this operation and the seeder it needs already shipped, so the gap is
the transport layer only.

- Contract: `_docs/openapi.yaml` line 1143 `paths./api/v1/admin/reset.post`, `operationId`
  `resetData`, `tags: [admin]`, request body `$ref: '#/components/schemas/ResetDataRequest'`
  (line 1972: `required: [confirm]`, `confirm` is `type: string` with `enum: [RESET]`), and
  responses `204` / `401` (`components.responses.Unauthorized`) / `403` / `422`
  (`components.responses.ValidationError`). The document-level `security: [bearerAuth: []]` covers
  it - the operation declares no `security` override of its own, unlike the `security: []` the
  public and health operations carry.
- Measured, and it matters: the contract's `403` example carries `error.code: INTERNAL_ERROR`.
  `_docs/specs.md` section 11 (line 447) lists 13 codes, and `FORBIDDEN` is NOT one of them;
  `backend/app/errors.py` builds `ERROR_CODES` from exactly that table, so
  `AppError("FORBIDDEN")` raises `ValueError: Unknown error code: FORBIDDEN` at runtime - measured:
  `FORBIDDEN in ERROR_CODES: False | size 13`. The 403 must therefore be raised as
  `AppError("INTERNAL_ERROR", message="Reset is only allowed in development", status_code=403)` to
  stay inside both the contract example and the shipped error machinery. A `FORBIDDEN` code would
  need a contract change owned by Platform Issue #3, which is out of scope here.
- Spec: `_docs/specs.md` line 131 lists "Reset data (development only)" under Admin; line 545 lists
  `POST /api/v1/admin/reset` under section 12 API Summary; line 317 gives `cancelled_reason` the
  enum `CUSTOMER | STAFF | CLOSED_DAY | RESET`.
- Reuse: `backend/app/seed.py` (B-13) already exposes `seed_data(reset: bool = False)`, and
  `reset=True` is the whole reset behaviour - `drop_schema` (drop_all), `create_schema`
  (create_all), then re-insert the fixture rows. Measured: the route that calls
  `seed_data(reset=True)` took a database whose `tables` and `waitlist_entries` rows had both been
  deleted (counts `0, 9` -> `0, 0`) back to `(10 tables, 9 entries, 1 restaurant)`. The endpoint
  must not re-implement any of that.
- Ownership, said plainly because three issues touch one file: **this issue EXTENDS
  `backend/app/routers/admin.py`, it does not own it.** B-10 owns the settings routes, B-11 owns the
  table routes (that branch already created the file), and this issue adds the one reset operation
  to the same `router`. Every AC below is a PRESENCE check on the reset behaviour, never an
  exclusivity check on the file: none of them asserts that `admin.py` did not exist before, and none
  of them asserts that any other admin route is absent. If this worktree later gains `admin.py`
  through a merge, the blocks measure the reset behaviour on top of whatever else the file carries.
- Environment mechanism, and the finding that comes with it: `backend/app/config.py` caches
  `get_settings()` with `@lru_cache`, and `backend/app/database.py` plus `backend/app/main.py` both
  read settings at IMPORT time. A test process therefore cannot select `ENV=production` by setting
  the environment variable after `app.main` is imported; it has to build
  `Settings(_env_file=None, env='production', ...)` and rebind `app.config.get_settings` before
  calling `app.main.app`, which is exactly what AC-4's block does. **Finding for SW: nothing in the
  app needs to change for that** - the AC drives the existing seam rather than asking for a new
  one, and if SW adds any production guard, it must keep reading the environment through
  `get_settings().env` so that rebinding stays the single supported test seam.

Related: B-13 (seeder), B-04 (error envelope), B-05 (staff JWT), B-10/B-11 (same router file).
Design: not a UI issue. Plan: `_docs/plan.md` phase 2.

  ```bash
  declared_norm = {(re.sub(r'\{[^}]+\}', '{}', p), v) for p, v in declared}
  # FastAPI's own documentation routes are not API endpoints and are exempt by name; anything else
  # the router serves but the contract does not declare is an invented endpoint (the point of the
  # AC), and reading the ROUTED table rather than app.openapi() also catches a handler mounted with
  # include_in_schema=False.
  DOC_ROUTES = {'/docs', '/redoc', '/openapi.json', '/docs/oauth2-redirect'}
  invented = sorted(p for p in (served - declared_norm) if p[0] not in DOC_ROUTES)
  missing = sorted(d for d in declared_norm if ('/api/v1/admin' in d[0] or '/api/v1/auth' in d[0]
                    or '/api/v1/public' in d[0] or d[0] == '/health') and d not in served)
  c = TestClient(app, raise_server_exceptions=False)
  health = c.get('/health').status_code
  problems = []
  if ('/api/v1/admin/reset', 'POST') not in served:
      problems.append('the served route table has no POST /api/v1/admin/reset')
  if invented:
      problems.append('the application serves path+verbs the contract does not declare: ' + str(invented))
  own_missing = [d for d in missing if d[0] == '/api/v1/admin/reset']
  if own_missing:
      problems.append('POST /api/v1/admin/reset is not routed at all')
  if health != 200:
      problems.append('/health answered ' + str(health) + ' to GET')
  if ('/health', 'GET') not in served:
      problems.append('the served route table has no GET /health')
  print('FAIL AC-10: missing ' + str(missing) + ' | invented ' + str(invented) + ' | health=' + str(health)
        if problems else
        'PASS AC-10: every served path+verb is declared in openapi.yaml (no invented route among ' + str(len(served)) + ' walked route+verbs), POST /api/v1/admin/reset is among them, and the shipped surfaces stay reachable (health=200; absent=' + str(missing) + ')')
  PY
  rc=$?
  rm -f /tmp/_b12ac10.db
  exit $rc
  ```

## Implementation notes

- Suggested files: create `backend/app/routers/admin.py` if B-10/B-11 have not already landed it, and
  add the one reset operation to the existing `router` if it has. Add `ResetDataRequest` to
  `backend/app/schemas.py` (`confirm: str = Field(..., pattern='^RESET')` or `Literal['RESET']` -
  either way the generated schema must name the model `ResetDataRequest`, which AC-9 checks).
- Mount it through `app.main.mount(admin_router.router)` next to the existing
  `mount(auth_router.router)` / `mount(public_router.router)` lines, and pass the one process
  limiter through a `configure_limiter(limiter)` hook if the file needs one. Do NOT add a rate limit
  to reset: specs.md section 9 budgets login, join and lookup only.
- Handler shape that satisfies every AC above (measured against this branch's app, 204/403/422/401
  all behaved as specified):
  `def reset_data(request: Request, staff: Staff, db: DbSession, payload: ResetDataRequest) -> Response`
  with `status_code=204` on the decorator, an env guard raising
  `AppError('INTERNAL_ERROR', message='Reset is only allowed in development', status_code=403)`
  BEFORE any data work, then `seed.seed_data(reset=True)`, then `return Response(status_code=204)`.
  Three details that ACs depend on: (1) return the `Response` annotation form so FastAPI writes no
  body and `response.text` stays `''` (AC-6) - returning `None` on a `204` route without the
  annotation risks a `"null"` body; (2) import the seeder as `from app import seed` and call
  `seed.seed_data(reset=True)` so a test that patches the module attribute can see the call (AC-8);
  (3) the `Staff` dependency must stay in the signature - dropping it silently deletes `security`
  from the generated document and turns AC-9 and AC-10 red.
- Guard order matters for AC-5 versus AC-4: body validation (422) runs before the handler body, so a
  malformed body answers 422 even in production. That is the contract's own ordering (the 422
  response is declared unconditionally), and AC-4 only demands that a well-formed request cannot
  reset outside development. Do not "fix" this by hand-parsing the body.
- Keep the message on the 403 non-empty: `AppError` defaults the message to the code with
  underscores replaced, and AC-3/AC-4 assert a non-empty `error.message`.
- Do NOT over-engineer: no background task, no audit log table, no confirmation token, no async
  wrapper. The whole endpoint is a guard, one seeder call and a 204.
