## Reason (audit provenance)

SEC AUDIT MEDIUM (A-5 A-13, D-9 header half): 500s bypass header middleware entirely; no CSP/HSTS/Cache-Control anywhere; 3000-char caller-supplied X-Request-ID reflected. Severity medium.

## Context

`backend/app/main.py` ships a `HeadersMiddleware` (a `BaseHTTPMiddleware`) that mints/echoes `X-Request-ID` and stamps `X-Content-Type-Options`, `X-Frame-Options`, and `Referrer-Policy` on the way out. The phase-5 security audit (A-5, A-13, D-9 header half) found four gaps: (1) error responses produced by the exception handlers in `backend/app/errors.py` do not reliably carry the security headers; (2) no Content-Security-Policy is set anywhere; (3) the caller-supplied `X-Request-ID` is reflected verbatim with no bound, so a 3000-char value is echoed back; (4) there is no Cache-Control policy and no HSTS. This issue closes the header half of D-9. Related: t21 (access log / request-id origin), t18 (error envelope).

## Acceptance criteria

- **AC-1 (error responses carry security headers)**: A forced 500 response (a route whose handler raises an unhandled exception) carries `X-Request-ID`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, and `Referrer-Policy: strict-origin-when-cross-origin` in its response headers, in addition to the contract 500 body. The exception-handler layer must sit inside the headers layer so 500s are not bypassed.
- **AC-2 (CSP on HTML responses)**: Every HTML response (a route returning `text/html`) carries a `Content-Security-Policy` header. Report-only (`Content-Security-Policy-Report-Only`) is acceptable as the first step; the directive must be non-empty.
- **AC-3 (X-Request-ID bounded)**: The `X-Request-ID` response header is at most 128 characters. When the caller supplies an `X-Request-ID` longer than 128 characters or an empty/whitespace value, the response carries a server-generated id (valid UUID4, <=128 chars) instead of reflecting the input. A valid supplied id (<=128 chars) is still echoed unchanged.
- **AC-4 (Cache-Control no-store)**: JSON responses from staff and admin surfaces and from `/api/v1` JSON endpoints carry `Cache-Control: no-store`.
- **AC-5 (HSTS gated)**: A `Strict-Transport-Security` header is emitted when the behind-the-proxy / HSTS setting is enabled, and is absent when the setting is disabled. The setting is a config flag, not hardcoded on.

## Out of scope

- Enforcing a full blocking CSP (report-only is the accepted first step; promotion to blocking is a follow-up).
- Rate-limiting, CORS allow-list, or access-log behaviour (t21, t23 — unchanged).
- The error envelope body shape (t18) — only the response headers on 500s are in scope here.
- Any client/frontend cache behaviour; only the server-issued `Cache-Control` header.

## Definition of Done

- All five ACs pass their verification commands.
- The forced-500 probe (AC-1) is a real test that raises through the exception handler and asserts the four headers, not a mocked response.
- No existing `test_middleware.py` test is weakened; the pre-existing request-id echo and security-header assertions still pass.
- The HSTS flag defaults to disabled so behaviour is unchanged until a deployment opts in.
