## Metadata

- **Source**: SEC AUDIT MEDIUM (B-4 + A-5-adjacent) — consolidated from the phase-5 audit
- **Audit item**: B-4 (MEDIUM: locked → 500 `INTERNAL_ERROR` indistinguishable from a crash; the per-request busy timeout of 30s parks workers; `journal_mode=delete` means readers block behind the writer), A-5-adjacent (500s carry no `X-Request-ID` — the correlation half)
- **Audit finding**: `sqlite3.OperationalError: database is locked` — produced whenever the single SQLite file is held by another writer — is not mapped anywhere in `backend/app/errors.py`, so it falls through the generic `Exception` handler and answers 500 `INTERNAL_ERROR`, the same code a crash produces. Until the request's `timeout: 30` busy-wait expires, the worker thread is parked on the lock (up to 30s per request, and there is no cap on how many requests queue behind the same holder). With the default journal mode (`delete`), a reader behind an exclusive write transaction blocks for the full timeout as well. And when the 500 finally arrives, it carries no `X-Request-ID` to correlate it with the request that caused the contention.
- **Phase**: phase-5-audit
- **Priority**: medium
- **Estimate**: M
- **Labels**: `audit`, `contract`, `backend`, `database`

## Reason (audit provenance)

SEC AUDIT MEDIUM (B-4 + A-5-adjacent), severity medium:

> sqlite database-is-locked maps to 500 INTERNAL_ERROR indistinguishable from a crash; the per-request busy timeout of up to 30s parks workers; `journal_mode=delete` means readers block behind the writer; 500s carry no X-Request-ID (correlation gap).

Acceptance as seeded: sqlite database-is-locked maps to 503 (or a contract code) with `Retry-After` instead of 500 `INTERNAL_ERROR`; the per-request busy timeout is shortened from 30s to a documented value; WAL is enabled OR the single-writer constraint is documented at the config site; the GET that writes (`_sweep_expired`) is audited and moved out of the read path or made contention-safe; a measured probe with a concurrent external writer shows clients get typed retryable responses and zero 500s.

## Goal

When this is done: a busy/locked SQLite store is a contract outcome, not a crash. Any request that touches the store while an external writer holds the file lock is answered with the typed retryable — a 503 carrying a `Retry-After` header and the contract error envelope, with an `error.code` that is a 503 row of the `_docs/specs.md` §11 table — never a silent 500. The per-request busy timeout is a documented, sub-30s value that actually bounds the park (a blocked request fails fast, not after 30s). The journal-mode decision is explicit: the store runs in WAL (readers no longer block behind the writer) or the single-writer constraint is documented at the config site where the operator sets `DATABASE_URL`. The read path that writes — the staff waitlist GET that sweeps lapsed no-shows — is contention-safe (a blocked sweep answers the typed 503) or moved out of the read path, and the section 4.10 sweep still persists after the lock clears. And a deterministic measured probe — a second connection holding `BEGIN EXCLUSIVE` — proves all of it end-to-end: typed retryable responses under contention, zero 500s, healthy answers after release.

## Context

- **Audit provenance**: see the Reason section. The X-Request-ID half (500s carrying no correlation header) belongs to the header layer and is owned by t26 — out of scope here.
- **Grounding facts at the groom base `75eab5d`, Windows + git-bash host**:
  - `backend/app/database.py` creates the engine with `connect_args={"check_same_thread": False, "timeout": 30}` — the 30 is SQLite's per-request busy timeout, bound as an undocumented literal. A store locked by an external writer parks the request's worker for up to 30s, and the resulting `sqlite3.OperationalError: database is locked` is not mapped in `backend/app/errors.py` (handlers: `AppError`, `RequestValidationError`, `RateLimitExceeded`, `StarletteHTTPException`, generic `Exception`), so it answers 500 `INTERNAL_ERROR` through the generic handler — indistinguishable from a crash.
  - No `PRAGMA journal_mode` is set anywhere in `backend/`; the store runs on SQLite's default `journal_mode=delete`. Measured on this host against the app's own engine: with a second connection holding `BEGIN EXCLUSIVE`, a third connection's **write** blocks and then fails `sqlite3.OperationalError: database is locked` under both `delete` and `wal`; under `delete` a third connection's **read** also blocks the same way, while under `wal` the read is unaffected. The verification probes use the write request as the lock trigger (effective under both journal modes) and accept 200-or-503 for a read under the lock (journal-mode dependent) — but never 500.
  - `_docs/specs.md` §11 (Error Codes) carries **no 503 row at all** — the table's statuses end at `INTERNAL_ERROR` 500 — and the string `Retry-After` appears nowhere in `backend/`. The retryable outcome does not exist in the contract yet: the builder must add the 503 row to §11 (the `ERROR_CODES` loader in `errors.py` parses the table) and answer busy/locked with that code plus the `Retry-After` header.
  - The write-on-GET path: `backend/app/services/staff_waitlist.py::list_waitlist` (line 376) calls `_sweep_expired` before reading, and `_sweep_expired` → `guest_rules.apply_lazy_no_show` flips the branch's lapsed `CALLED` rows to `NO_SHOW` and **commits inside the staff-list GET** — the section 4.10 lazy no-show, a write inside the read path.
  - Measured adjacent finding (auth layer, out of scope for this issue): under a held `BEGIN EXCLUSIVE` lock a staff-authenticated `GET /api/v1/staff/waitlist?status=ALL` answers **401 `AUTH_TOKEN_EXPIRED`** (not 500) after the verifier's per-request key rebuild — `select token_generation from settings` in `token_generation_value` (`app/routers/auth.py`) fails on the held lock and its blanket `except Exception` swallows the failure into `INITIAL_TOKEN_GENERATION`, so the token verifies against the wrong key and is misclassified as expired. This is the same B-4 misclassification family surfacing in the auth dependency; AC-4 therefore probes the read path at the service level, where the raw lock error is observable.
  - 500s currently carry no `X-Request-ID`: the correlation gap is the header-layer half and is owned by t26.
- **Green baseline (measured at the groom base `75eab5d`)**: `cd backend && .venv/Scripts/python.exe -m pytest tests -q -p no:randomly` → 340 passed, 2 xfailed, 3 warnings in 47.96s (rc 0); `cd backend && .venv/Scripts/ruff.exe check .` → "All checks passed!". The suite venv is Python 3.12.15; every verification block below pins `backend/.venv/Scripts/python.exe` (bare `uv` on this host would pick Python 3.13 and fail the auth-test teardown with WinError 32).

A third connection's write must fail under the held lock (probe sanity, exits loudly if the lock is not effective). The app is booted in-process with `TestClient` against a scratch database under `backend/.scratch/` (created by the app's own lifespan, removed on both exit paths), so no persistent state and no `test.db` is touched.

## Acceptance criteria

The contract promise being closed: SQLite busy/locked is answered as a contract outcome — a 503 with a `Retry-After` header and the contract envelope `{"error": {"code", "message", "details"?}}`, whose `code` is a 503 row of the `_docs/specs.md` §11 table — never as a silent 500 `INTERNAL_ERROR`; the park is bounded by a documented sub-30s busy timeout; the journal-mode decision is explicit (WAL or the single-writer constraint documented at the config site); and the read path that writes is contention-safe or moved, with the section 4.10 sweep still persisting after the lock clears.

AC-1 — A blocked write is a typed retryable, never a 500. With an external writer holding `BEGIN EXCLUSIVE` on the store file, a guest join (`POST /api/v1/branches/1/waitlist`) is answered 503 with a `Retry-After` header (integer seconds, 1..30) and the contract envelope (top level is exactly the `error` key; `error.code` / `error.message` are non-empty strings; `error.details`, if present, is an object; no `detail` key; `error.code` is not `INTERNAL_ERROR` and **is a 503 row in the `_docs/specs.md` §11 table** — the new row must exist there). ## Implementation notes

- (SW) The new 503 code: add the row to the `_docs/specs.md` §11 table (e.g. `SERVICE_UNAVAILABLE 503` or a store-specific code such as `STORE_BUSY 503`) — the `ERROR_CODES` loader in `errors.py` picks table rows up automatically, and AC-1's probe requires the responded code to be a 503 row there.
- (SW) The busy mapping: a handler in `backend/app/errors.py` for the store-busy exception path — the `OperationalError` / `SQLAlchemyError` carrying SQLite's "database is locked" — answering that 503 code, the envelope, and `Retry-After: <the documented busy timeout or a fixed small integer seconds>`. It must not swallow other `OperationalError`s (e.g. "no such table") as 503s — only the busy/locked signature maps.
- (SW) The busy-timeout binding: a named constant (UPPER_SNAKE_CASE) or a `Settings` field in `backend/app/config.py`, referenced by `connect_args={"timeout": ...}` (or a `PRAGMA busy_timeout` at engine init), documented at the site with the busy/lock semantics, expressed in seconds (0.5..10).
- (SW) The journal mode (WAL arm): `PRAGMA journal_mode=wal` at engine init — a SQLAlchemy `connect` event listener is the idiom for a NullPool engine. Or keep the default mode and take the documentation arm of AC-3.
- (SW) The sweep: the AC-1 busy handler already makes `_sweep_expired`'s commit contention-safe (a blocked sweep answers the typed 503, AC-4 accepts that), so the minimal fix is the handler plus the timeout; re-homing the sweep to the join-write path is an alternative but must keep the NO_SHOW visible to the AC-4 probe (request-driven on the staff-list read or the join write).
- (SW) Windows + git-bash host: every verification block pins `backend/.venv/Scripts/python.exe` (Python 3.12.15) and never calls bare `uv` (which would pick Python 3.13 and fail the auth-test teardown with WinError 32). The probes use only the stdlib `sqlite3` for the external writer.
