- **Audit finding**: `errors.py` only maps `AppError`/`RequestValidationError`/`RateLimitExceeded`/generic `Exception`; uvicorn oversized-request-line 400s and FastAPI router 404s (path traversal / unmatched prefixes) escape the contract envelope; the capacity-reject 422 carries no `details.fields` (parity gap with schema-level 422s); the T32 conformance sweep does not assert the envelope shape on 401/405/429/500/503.
- **Phase**: phase-5-audit

## Reason (audit provenance)

SEC AUDIT LOW (B-6) + MEDIUM (B-12.2/B-12.3), consolidated:

> `errors.py` maps only AppError/RequestValidationError/RateLimitExceeded/generic Exception to the `{error: {...}}` envelope. The uvicorn oversized-request-line 400 (plaintext "Invalid HTTP request sent") and the FastAPI router 404 (traversal paths → plain Not Found, not the envelope) escape it. Service 422s (capacity rejects) carry no `details.fields` (parity with schema-level 422s), and the T32 conformance sweep does not assert envelope shape on 401/405/429/500/503.
>
> Acceptance: uvicorn oversized-request-line 400 and FastAPI router 404 (traversal / unmatched prefix) produce the contract error envelope OR are documented as edge-owned with contract-mapping middleware; capacity-reject 422 carries `details.fields` naming the field (parity with schema-level 422s); the conformance sweep test asserts envelope shape on the 401/404/405/409/422/429/500/503 classes.

## Goal

When this is done: every error status the application itself can produce — including router-level 404/405 refusals — is answered with the single contract shape `{"error": {"code", "message", "details"?}}`; the service-level capacity-reject 422 carries `details.fields` naming the field, on parity with schema-level 422s; the one 400 the app cannot own (the edge's oversized request line) is documented as edge-owned with the in-app contract mapping; and the conformance sweep asserts that shape on all eight non-2xx classes the contract can produce, so a regression in any of them goes red.

## Acceptance criteria

The contract promise being closed: every error status the application itself can produce is answered in the shape `{"error": {"code": <non-empty string>, "message": <non-empty string>, "details": <object, only when non-empty>}}` — top level is exactly the `error` key, and the framework-default `detail` key never leaks through. This issue closes two known gaps (router-level 404/405, and the service-level 422 without details), documents the one the app cannot own (the edge's oversized-request-line 400), and extends the conformance sweep to all eight non-2xx classes the contract can produce.

AC-1 — Router-level refusals (404/405) are answered with the contract envelope. Any path the router does not serve — a made-up `/api/v1/...` prefix, or a traversal-style request that arrives as an unmatched prefix — is answered 404 with the contract envelope (JSON; top level is exactly the `error` key; `error.code` and `error.message` are non-empty strings; `details`, if present, is an object; no `detail` key). Any method the router does not allow on a mounted path (e.g. `DELETE /health`) is answered 405 with the same envelope shape. Both must be produced by the app's own error layer (a registered `StarletteHTTPException` handler or a contract-mapping middleware in `backend/app/errors.py` / `backend/app/main.py`), not by the framework default. If a new error code is introduced for these refusals, it is added to the `_docs/specs.md` §11 table so the `ERROR_CODES` loader picks it up; reusing an existing 404-class code is also acceptable. Test: new TestClient cases in the conformance surface (`backend/tests/`).

Measured at the groom base `3669b00`, Windows + git-bash: `FAIL AC-1: router-level 404/405 refusals do not carry the contract error envelope` (exit 1) — all four probes (three unmatched-path 404s, one traversal-style, one wrong-method 405 on `/health`) answer the framework-default `{"detail": "Not Found"}` / `{"detail": "Method Not Allowed"}` — the B-6 gap.

AC-2 — The oversized-request-line 400 is documented as edge-owned. `_docs/specs.md` §11 (Error Codes) carries an explicit note stating (a) that an oversized request line is rejected by the edge (uvicorn's HTTP parser; plaintext "Invalid HTTP request sent", HTTP 400) before the request reaches the application, so it can never carry the app's error envelope, and (b) that the in-app router-level refusals (404/405) are the surface the app maps to the envelope (the AC-1 handler is that contract-mapping layer). This is the documentation arm of the audit's OR clause: the edge 400 cannot be intercepted in-app, so the contract promise for it is the documentation, and the 404/405 envelope is the contract-mapping half.

Measured at the groom base `3669b00`, Windows + git-bash: `FAIL AC-2: _docs/specs.md section 11 does not document the oversized-request-line 400 as edge-owned with the in-app 404/405 contract mapping` (exit 1) — §11 carries neither an oversized/request-line note nor any 405 mention.

AC-3 — The capacity-reject 422 carries `details.fields` naming the field. The service-level capacity reject — `PATCH /api/v1/admin/tables/{id}` with an out-of-range capacity the request schema admits (e.g. `capacity: 21` or `capacity: 0`; `UpdateTableRequest.capacity` declares no bounds, and the bound is re-checked in the service) — is answered 422 `VALIDATION_ERROR` with `error.details.fields`, a non-empty `field -> message` map whose key set is exactly `{"capacity"}` — the same shape the schema-level 422 carries. Parity: the schema-level capacity reject (`POST /api/v1/admin/tables` with `capacity: 21`) still carries `details.fields` naming `capacity`. Neither reject changes status (422) or code (`VALIDATION_ERROR`). Sibling service rejects in the same module (label / section / sort_order) may receive the same `details.fields` shape, but this AC does not require it. Test: new TestClient cases against the admin-tables surface.

Measured at the groom base `3669b00`, Windows + git-bash: `FAIL AC-3: the service capacity-reject 422 does not carry details.fields naming the field (schema-level parity checked too)` (exit 1) — `PATCH` `capacity: 21` and `capacity: 0` both answer 422 `VALIDATION_ERROR` with no `details` at all; the schema-level create parity case already carries `details.fields`.

AC-4 — The conformance sweep asserts the envelope shape on the eight non-2xx classes. The conformance sweep (`backend/tests/test_e2e_contract.py`, the T32 surface, extended by t16) is extended so that each of the eight status classes the contract can produce — 401, 404, 405, 409, 422, 429, 500, 503 — is probed and the envelope shape is asserted (top level is exactly `error`; `error.code` / `error.message` are non-empty strings; `details`, if present, is an object; no `detail` key). Where the product already produces a class naturally, the probe uses the real contract answer (401 invalid PIN / expired token; 404 unmatched route; 405 method-not-allowed; 409 duplicate phone / invalid status transition; 422 malformed body; 429 guest-budget burst; 500 unhandled exception through the registered handler; 503 forced through the app's own error layer via a status override — the real producer lands with t19). The existing sweep coverage (the t16 surface) still passes.

Measured at the groom base `3669b00`, Windows + git-bash: `FAIL AC-4: the conformance sweep does not assert envelope shape on all eight classes - no reference to status class 405; no reference to status class 429; no reference to status class 500; no reference to status class 503` (exit 1; the run arm — the sweep's current tests — is green at HEAD per the full-suite baseline below).

AC-5 — Backend floor green, no regressions, no lint. The full backend suite (`cd backend && .venv/Scripts/python.exe -m pytest tests -q -p no:randomly`) exits 0 with a summary of at least 335 passed (the groom baseline; new AC tests may grow the count) and exactly 2 xfailed (the pre-existing set — no new `xfail` and no `skip`), and nothing else in the summary (no failed, no errors).
