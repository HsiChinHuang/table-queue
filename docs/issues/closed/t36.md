## Context

Test-infrastructure reliability issue observed during T11 #66 QA on the merged T23
rate-limiting work (T23 itself merged and closed green; this is NOT a product regression).
The three X-Forwarded-For / trusted-proxies tests in `backend/tests/test_rate_limit_t23.py`
intermittently fail depending on test execution order:

- In `-p no:randomly` (fixed order): 2 of the XFF tests failed on the first run, passed on
  immediate re-run.
- In `--randomly-seed=42`: 3 of the XFF tests failed on the first run, passed on immediate
  re-run.
- In default random mode: green.
- All failing tests pass in isolation.
- Failing tests (observed): `test_xff_not_honoured_when_trusted_proxies_unset`,
  `test_xff_honoured_when_trusted_proxies_names_the_proxy`,
  `test_xff_not_honoured_when_trusted_proxies_names_a_different_proxy`.

This issue removes the shared-state mutation mechanism the XFF tests currently rely on and
makes the stability guarantee testable, on the current native-Windows host.

## Root cause

Confirmed by recon of the two files that own the mechanism (this grooming):

- The exact shared state is the **module-level `app.main.limiter` singleton and its
  process-wide counter store**, plus the **`@lru_cache`d `app.config.get_settings()`
  singleton**. Both are process-wide, and the XFF tests mutate both in place:
  - `limiter_on_fresh_store()` (a test-local `contextlib.contextmanager`, not a pytest
    fixture) rebinds `limiter._storage` and `limiter._limiter` to a fresh
    `BoundedFrozenClockMemoryStorage` and flips `limiter.enabled = True`, relying on a
    `finally` to restore the previous instance/flag.
  - `trusted_proxies(value)` (same shape) rewrites `settings.trusted_proxies` on the cached
    `Settings` instance in place; `app.services.rate_limit.get_rate_limit_key` reads that
    field on EVERY request, so any test running while the mutation is live - or any test
    that runs after a restore that did not happen (crash, interrupt, a future test that
    raises between the two context managers) - observes a different client-IP resolution
    (trusted-proxy vs direct), which flips the 5/minute login budget's 429/200 expectation.
- The isolation is therefore save/restore bookkeeping inside the test body, not
  fixture-scoped isolation: the swap lives in the test module, teardown correctness depends
  on the test body's own control flow, and the state shared with every other test in the
  process (the `conftest.py` autouse `disable_limiter` fixture reads and writes the same
  `limiter.enabled` flag around every test) is the same object. That is the
  order-dependence: what a later test observes depends on what an earlier test's
  save/restore left behind, and only on the happy path.
- The suite's established isolation pattern is fixture-scoped (the `conftest.py` autouse
  fixtures, the per-test scratch DB file in `tq_isolated`, the dedicated
  `_db_test_support.Database` file+engine pattern): state a test needs is created for the
  test and torn down by fixture teardown, never by in-place mutation of a process-wide
  object that other tests also read.

**Groom baseline on THIS host (native Windows, main repo, this grooming):** the XFF file
alone (`tests/test_rate_limit_t23.py`, `-p no:randomly`) ran **3/3 green** (`7 passed` each,
~6.2 s); the two-file order `tests/test_auth.py tests/test_rate_limit_t23.py` (the auth file
exercises the same limiter routes and runs first) ran **3/3 green** (`29 passed` each,
~18.2 s); the full suite ran **1/1 green** (`388 passed, 2 xfailed`, ~85 s). The
order-dependent flake does not reproduce here; per the t35 precedent the AC is the stability
guarantee plus removal of the shared-state mutation mechanism, not a repro.

## Design

Make the XFF tests isolated from the shared limiter state by fixture-scoped isolation,
matching the codebase's established test-isolation patterns. No production code
(`backend/app`) changes - the limiter and the key function are correct; only the test's
isolation is the defect.

1. **Stop mutating the process-wide `limiter` in place.** The XFF tests (and the other two
   burst tests that use the same helper) must get their fresh counter store through a pytest
   fixture - e.g. a fixture that builds a dedicated limiter/storage instance (or
   monkeypatches the reference the request path reads) and tears it down in fixture
   teardown - instead of the test-local `limiter_on_fresh_store()` contextmanager that
   rebinds `limiter._storage` / `limiter._limiter` / `limiter.enabled` by hand. The
   `conftest.py` autouse `disable_limiter` fixture keeps owning `limiter.enabled` for the
   rest of the suite; the XFF fixture layers on top of it and is undone by its own teardown.
2. **Stop rewriting the cached `Settings` in place.** The `trusted_proxies(value)`
   contextmanager must become a fixture (or a `monkeypatch`-based helper) so the
   `TRUSTED_PROXIES` value the key function reads is scoped to the test and restored by
   fixture teardown - e.g. `monkeypatch.setattr` on the settings instance or an override of
   the `get_settings` reference the rate-limit module reads - never a bare
   `settings.trusted_proxies = value` with a hand-written `finally`.
3. **Keep the key-function unit test as-is or fixture-ise it the same way**:
   `test_rate_limit_key_honours_only_a_named_proxy` currently uses the same
   `trusted_proxies()` helper; it must not keep the in-place mutation either.
4. **No assertion weakening:** the file keeps its exact 7 test ids and its assertion lines
   are not reduced (pre-fix baseline: 27 `assert ` lines; file run summary `7 passed`).

## Acceptance criteria

- AC-1 (stability, demonstrated order): running `pytest tests/test_auth.py tests/test_rate_limit_t23.py -q -p no:randomly` 10 consecutive times yields 10 green runs (exit 0 each, `29 passed`, no XFF failure in any run). The tracked `backend/test.db` is restored after the loop.
- AC-2 (stability, XFF file): running `pytest tests/test_rate_limit_t23.py -q -p no:randomly` 10 consecutive times yields 10 green runs (exit 0 each, `7 passed`). The tracked `backend/test.db` is restored after the loop.
- AC-3 (suite): the full backend suite (`pytest -q -p no:randomly`) exits 0 with no failures or errors, at the groom baseline of `388 passed, 2 xfailed`; `backend/test.db` restored afterwards.
- AC-4 (mechanism removal): `tests/test_rate_limit_t23.py` performs no in-place mutation of the shared limiter or the cached settings - no `limiter._storage =`, no `limiter._limiter =`, no `limiter.enabled =`, no `settings.trusted_proxies =` (or equivalent in-place attribute write) remains in the file - and the isolation it needs is provided by a pytest fixture (`@pytest.fixture` present in the file) whose teardown restores the state. FAILS pre-fix (the current file does exactly these in-place assignments).
- AC-5 (no assertion weakening, invariant - PASSES pre-fix by design): the file still collects exactly 7 tests, its run summary is `7 passed`, and its `assert ` line count is >= 27 (the pre-fix baseline).
- AC-6 (test-infra only): no production code changes - `git status --porcelain backend/app` and `git diff --name-only HEAD -- backend/app` are both empty (the diff touches only `backend/tests/`).
- AC-7 (scope honesty, documentation - PASSES by construction): this spec states the scope explicitly: the order-dependent flake does not reproduce on this native-Windows host (groom baseline 3/3 + 3/3 + 1/1), the fix removes the shared-state mutation mechanism (in-place rebind of the module-level `app.main.limiter` store/strategy/enabled flag and in-place rewrite of the cached `get_settings()` `trusted_proxies`), and the guarantee on this host is the 10/10 stability of the demonstrated order and the file plus that mechanism removal.

## Out of scope

- Reproducing the original order-dependent flake on this host: it does not reproduce in the
  groom baseline (3/3 file, 3/3 order, 1/1 suite) and no other host/runner is part of this
  repo's verification; the AC is the stability guarantee plus mechanism removal.
- Changes to `backend/app` production code: the limiter, its storage class and the
  `get_rate_limit_key` rule are correct for production; only the tests' isolation is the
  defect.
- Changing the non-XFF tests' behaviour or any other test module: the diff is confined to
  `backend/tests/test_rate_limit_t23.py` (and, if the fixture needs shared plumbing,
  `backend/tests/conftest.py`); `conftest.py`'s existing autouse fixtures keep their
  semantics.
- The pre-existing fact that `backend/test.db` is a tracked file (separate hygiene concern).
