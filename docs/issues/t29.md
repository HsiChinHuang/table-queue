## Context

The security audit (phase-5) flagged that integer and length bounds are not consistently
declared at the request boundary, so two distinct failure modes exist on live routes:

- **A-6 (overflow-500 on unauthenticated path params).** The public branch routes
  (`GET /api/v1/public/branches/{branch_id}`, `GET .../board`, `POST
  /api/v1/branches/{branch_id}/waitlist` in `backend/app/routers/public.py`) bind
  `branch_id: int` with no `ge`/`le`. A value beyond SQLite INTEGER max
  (`9223372036854775807`) is a valid Python `int`, passes FastAPI, reaches
  `service.branch_info` -> `db.get(Branch, branch_id)`, and raises
  `OverflowError: Python int too large to convert to SQLite INTEGER`, which the catch-all
  renders as a **500 `INTERNAL_ERROR`** on an endpoint that requires no auth.
- **B-3 (body sort_order OverflowError 500 + out-of-domain value persisted).**
  `CreateTableRequest.sort_order` and `UpdateTableRequest.sort_order`
  (`backend/app/schemas.py`) declare no bounds, and the service-layer
  `_reject_int` (`backend/app/services/tables.py`) only checks `isinstance(int)` — it does
  not check range. So `sort_order=9223372036854775808` on `POST`/`PATCH
  /api/v1/admin/tables` reaches `db.commit()` and 500s, while
  `sort_order=9223372036854775807` (SQLite INTEGER max) is **persisted** because nothing
  prices an upper bound.
- **capacity create/update bound disagreement.** `CreateTableRequest` declares
  `capacity: ge=1 le=20` and `label: min_length=1 max_length=10`, but
  `UpdateTableRequest` declares **no bounds** on `capacity` or `label` (only `section`
  carries `max_length=50`). The update path answers 422 today only via the service-layer
  `_reject_capacity`/`_reject_label`, so the bound lives in two places and disagrees about
  where it is enforced.
- The staff waitlist list route (`backend/app/routers/staff_waitlist.py`,
  `GET /api/v1/staff/waitlist`) binds `limit: int = Query(default=100)` and
  `offset: int = Query(default=0)` with no `ge`/`le`, so a negative `limit`/`offset`
  answers **200** rather than 422.

`party_size` already carries `ge=1 le=20` on both `JoinWaitlistRequest` and
`EditWaitlistRequest` and on the list query param; it is in scope only to confirm the bound
is preserved, not to change it.

The fix belongs at the request boundary (schemas + route `Query`/path params), sized to
SQLite INTEGER (`le=9223372036854775807`) and to the domain, with the service-layer
`_reject_int` retained as belt-and-braces. See `docs/plan.md` (security-audit remediation
milestone) and the audit batch.

## Acceptance criteria

- **AC-1 — Table request schemas carry explicit bounds.** `CreateTableRequest.sort_order`
  and `UpdateTableRequest.sort_order` each declare both a lower and an upper bound;
  `UpdateTableRequest.capacity` declares `ge=1 le=20` and `UpdateTableRequest.label` declares
  `min_length=1 max_length=10` — i.e. `UpdateTableRequest` matches `CreateTableRequest`'s
  bounds. Checked by introspecting the generated JSON schema (constraints may sit in an
  `anyOf` for optional fields).
- **AC-2 — sort_order overflow is 422, not 500.** Sending `sort_order=9223372036854775808`
  to `POST /api/v1/admin/tables` and to `PATCH /api/v1/admin/tables/{id}` each returns 422
  `VALIDATION_ERROR` whose `error.details.fields` names `sort_order` — never a 500
  `INTERNAL_ERROR`.
- **AC-3 — negative limit/offset is 422, not 200.** A negative `limit` and a negative
  `offset` on `GET /api/v1/staff/waitlist` each return 422 — never a 200 that silently pages.
- **AC-4 — unauth branch_id overflow is 422, not 500.** An out-of-domain `branch_id` path
  value (e.g. `99999999999999999999`) on the unauthenticated public branch routes returns 422
  — never a 500 `OverflowError`.
- **AC-5 — bounds sized to SQLite INTEGER and domain, not over-tightened.**
  `sort_order=9223372036854775807` (SQLite INTEGER max) on create returns 201 and
  `capacity=20` on create returns 201.
- **AC-6 — service-layer `_reject_int` is belt-and-braces.** Calling
  `app.services.tables._reject_int` directly with `9223372036854775808` raises an `AppError`
  with status 422 (a range guard), so a value that slips the schema still cannot reach the DB
  as a 500.

## Verification commands

All commands run from the repo root (or `backend/`) on this host using the frozen venv.
`ac1` is a static introspection (no HTTP); `ac2`–`ac5` drive the app through `TestClient`
against a throwaway SQLite file; `ac6` calls the service guard directly. Each exits 0 on pass
and non-zero on fail.

- ac1:
  ```bash
  cd backend && ENV=development DATABASE_URL=sqlite:////tmp/t29ac.db JWT_SECRET=t29repro-0123456789-abcdefghijklmnopqrstuvwxyz-abcd1234 STAFF_PIN=0000 TZ=UTC ./.venv/Scripts/python.exe -c "
  from app.schemas import CreateTableRequest as C, UpdateTableRequest as U
  def conds(s):
      out=[]
      def rec(x):
          if isinstance(x,dict):
              for k,v in x.items():
                  if k in ('minimum','maximum','minLength','maxLength'): out.append((k,v))
                  rec(v)
          elif isinstance(x,list):
              for v in x: rec(v)
      rec(s); return dict(out)
  cs=conds(C.model_json_schema()['properties']['sort_order'])
  assert 'minimum' in cs and 'maximum' in cs, ('CreateTableRequest.sort_order unbounded', cs)
  us=conds(U.model_json_schema()['properties']['sort_order'])
  assert 'minimum' in us and 'maximum' in us, ('UpdateTableRequest.sort_order unbounded', us)
  uc=conds(U.model_json_schema()['properties']['capacity'])
  assert uc.get('minimum')==1 and uc.get('maximum')==20, ('UpdateTableRequest.capacity', uc)
  ul=conds(U.model_json_schema()['properties']['label'])
  assert ul.get('minLength')==1 and ul.get('maxLength')==10, ('UpdateTableRequest.label', ul)
  print('ac1 ok')
  "
  ```

## Out of scope

- Changing `party_size` bounds (already `ge=1 le=20` on `JoinWaitlistRequest`,
  `EditWaitlistRequest`, and the list query param) — preserved, not modified.
- Changing the `404`/`409` semantics of the public branch routes for an in-domain but
  non-existent `branch_id` (that is the existing `get_branch_or_404` behaviour, not an
  overflow concern).
- Rewriting the service-layer `_reject_capacity`/`_reject_label`/`_reject_section` beyond
  what is needed to keep `_reject_int` as a range guard; their current 422 behaviour is kept.
- Any change to `section` length bounds, `is_active`, or the reorder `ordered_ids` list.
- Multi-branch authorisation or cross-branch id handling (a separate concern).
- Adding or tightening bounds on `limit`/`offset` beyond `ge=0` (a domain page-size cap is a
  product decision, not part of this overflow fix).

## Definition of Done

- [ ] `CreateTableRequest.sort_order` and `UpdateTableRequest.sort_order` declare explicit
      `ge`/`le` sized to SQLite INTEGER (`le=9223372036854775807`).

- [ ] `branch_id` path params on the public routes and `limit`/`offset` query params on the

- [ ] All six verification commands above exit 0.
- [ ] No out-of-domain integer is persisted; no overflow reaches the 500 handler.
- [ ] `backend/test.db` is not committed (repros use a throwaway `/tmp` file).
