## Summary

Test-infra flake: the X-Forwarded-For / trusted-proxies tests in `backend/tests/test_rate_limit_t23.py` intermittently fail depending on test execution order, due to shared rate-limiter state leaking between tests.

## Observed behaviour (QA observation, T11 #66, to be confirmed by SW)

- In `-p no:randomly` (fixed order): 2 of the XFF tests failed on the first run, passed on immediate re-run.
- In `--randomly-seed=42`: 3 of the XFF tests failed on the first run, passed on immediate re-run.
- In default random mode: green.
- All failing tests pass in isolation.
- Failing tests (observed): `test_xff_not_honoured_when_trusted_proxies_unset`, `test_xff_honoured_when_trusted_proxies_names_the_proxy`, `test_xff_not_honoured_when_trusted_proxies_names_a_different_proxy`.

## Why it matters

This is a pre-existing test-infra issue (T23 rate-limiting was merged and closed green). It is NOT a product regression. But it can cause false failures in full-suite QA runs — including the T13 final regression gate — if the limiter state is not reset between tests.

## Hypothesis (to be confirmed by SW)

The rate limiter holds shared in-memory state (per-worker store) that is not reset between tests. When tests run in a certain order, a prior test leaves the limiter in a state that causes a later XFF test to see a different client-IP resolution (trusted-proxy vs direct), flipping the 429/200 expectation.

## Acceptance criteria (target)

- 10 consecutive full-suite runs (all three pytest modes: default random, `-p no:randomly`, `--randomly-seed=42) are green with 0 failures in `test_rate_limit_t23.py`.
- The limiter state is reset between tests (fixture or per-test isolation), so the XFF tests are order-independent.
- No product behaviour change (the rate limiter itself is correct; only the test isolation is fixed).
